# Chapter 10: 多 Agent 协作

## Core Idea
单个 Agent 受限于模型能力边界和上下文窗口;让多个 Agent 协同工作,意义不只是"取长补短",更根本的是**群体智能可能高于个体**——人类文明经由分工、协作、辩论和知识累积展现出远超任何天才个体的智能,Agent 群体同样可能涌现集体智能。多 Agent 协作因此不仅是突破单模型上下文窗口与能力边界的工程手段,更可能是从"专家级 AI"迈向"超越人类整体"的一条根本路径(Google DeepMind《从 AGI 到 ASI》把"大规模多 Agent 集体"列为通往 ASI 的关键路径;OpenAI 五级分类里 Level 5"组织"也常被类比为多 Agent 通向的终态)。本章全部工程方案都建立在两个正交设计维度之上:**上下文是否共享**,以及**协作拓扑如何组织**。整套抽象的蓝本来自操作系统——Agent 之于运行时,恰如进程之于内核。

## Frameworks Introduced

- **维度一·上下文是否共享**(决定 Agent 间如何传递信息的最基础架构决策):
  - **共享上下文(继承式协作)**:后一个 Agent 接收前一个 Agent 的完整轨迹,换系统提示词和工具集后成为新角色但保留全部记忆。信息零损耗、可回顾任何阶段细节;**代价是上下文快速膨胀**。类比:团队围坐一桌所有人听到所有话。对应 OS 是**线程**(共享地址空间、切换开销小、但无隔离)
  - **不共享上下文(隔离式协作)**:每个 Agent 维护完全独立的上下文和轨迹,无法直接访问对方的"思考过程",必须通过显式通信机制传递信息。模块化、隔离性好、可大规模并行;**代价是信息同步与调试复杂**。类比:不同部门通过邮件文档协作。对应 OS 是**进程**(各有独立地址空间、隔离彻底、但通信须经显式 IPC)
  - 经验法则:累计上下文预期超窗口 50% 应不共享;信息零损耗是硬约束(如安全审查不应看到原始思考)应共享;多数实际系统采用"阶段切换式"——前几个 Agent 共享,信息饱和后切到不共享 + 显式 handoff。重要澄清:两种都是"真正的多 Agent"(每阶段提示词和工具集不同即不同 Agent),区别在协调方式——共享靠隐式协调(上下文本身传信息),不共享靠显式协调(文件/消息/结构化接口)

- **维度二·协作拓扑**(控制权和信息按什么结构流动;与上下文共享概念上独立、实践中相关——共享上下文时拓扑多退化为角色切换序列无架构决策可做;不共享时"信息如何流动、由谁协调"才成为必须显式设计的问题):
  - **对等协作(Peer)**:2-3 个平等身份 Agent 通过多轮迭代互相反馈,引入认知多样性。实现复杂度最低,适合快速原型和迭代改进
  - **管理者模式(Orchestration)**:一个中心化 Manager Agent 负责任务规划和调度,多个子 Agent 各负责特定子任务。适合 5+ 子任务、需动态调度、子任务间有复杂依赖
  - **去中心化模式(Decentralized)**:无运行时中心控制者,Agent 间以对等方式协作,每个自主决定何时向谁沟通(移交/请求反馈/报告问题)。适合职责对等、控制权需在 Agent 间自主流转的场景
  - 两维度构成 **2×3 矩阵**,但共享上下文那一行拓扑大多退化,故本章重点展开不共享上下文的三格。关联术语:微服务领域称管理者 vs 去中心化为**编排(orchestration)vs 编舞(choreography)**;2026 年流行的"Graph Engineering"是显式设计执行图(节点是 Agent/程序/人工),本章三种拓扑即其中的多 Agent 子集

- **三种通信机制**(不共享上下文时必须显式传递信息;对应 IPC 两大范式):
  - **工具调用参数**:上游把结构化数据作为参数传给下游工具,随调用同步传递。适合类型确定、结构清晰、拓扑固定、Agent 少的场景
  - **共享文件系统**(Agent 世界的"共享内存"):Agent 读写共享目录下中间产物。适合产物较大或需持久化。快,但并发冲突留给使用者(需乐观锁/worktree)
  - **消息总线(Message Bus)**(Agent 世界的"消息传递"):专门在 Agent 间转发消息的中转站,Agent 不直接调用彼此而是发布到总线。天然支持异步(收发方不需同时在线),适合多 Agent 并行协调
  - 对应 IPC:工具调用参数和消息总线是"消息传递"的两种形态(前者同步、后者异步经中转)。Go 名言"不要通过共享内存来通信,而要通过通信来共享内存"——共享内存快却把并发冲突留给使用者,消息传递多写编排代码却让数据归属清晰可循。这个取舍在状态查询与并发冲突中反复出现

- **新信息判据**(判断多 Agent 何时真正优于单 Agent 的核心准则,2025 年一系列研究共识):协作过程是否引入了单个 Agent 在生成时无法获得的新信息?
  - **不引入新信息**(同模型自我审查、多 Agent 辩论同一段文本):等计算量下与单 Agent 持平甚至更差。Huang ICLR 2024 证实无外部反馈的自我纠正反而降准;TACL 2024 综述确认除非有可靠外部反馈否则自我纠正几乎不起作用;CRITIC 移除工具只保留自我评估时提升大部分消失。2026 Tran & Kiela 基于数据处理不等式解释:辩论中 Agent 处理相同文本,串行传递中间结论只可能丢信息、不可能凭空创造
  - **引入新信息**(Reviewer 用测试执行结果/渲染截图/外部工具验证):显著提升。RLEF(强化学习利用执行反馈)远超独立多次采样;WebGen-Agent 多层级视觉反馈让 Claude 3.5 Sonnet 从 26.4% 提到 51.9%
  - 解释了"学术说单 Agent 够、工程说多 Agent 好"的矛盾:学术比较多是"看着同一段文本讨论",工程有效的多 Agent 往往含外部反馈环路。对管理者模式的指导:Manager 应据任务复杂度动态分配步骤预算(单纯增加步骤数不能保证提升——Agent 缺乏"预算意识"会过早饱和)

- **提议者-审核者范式(Proposer-Reviewer)**:对等协作最经典的用途,直接落在新信息判据上。Proposer 生成候选成果,Reviewer 渲染执行结果用 Vision LLM/工具评估给出结构化反馈,反复迭代。Reviewer 的价值不是"用同一模型再看一遍",而在于引入了 Proposer 生成时无法获得的外部反馈(截图、测试结果、编译错误)。适用于安全审查、内容审核、代码审核(第 5 章已详述)

- **Loop 工程(Loop Engineering)**:把循环从模型提示词和聊天历史中抽离进持久控制面。核心共识——**循环的瓶颈在验证器而非模型**:验证不可靠,循环转得再快也只把劣质产出更快标记为完成。Boris Cherny:"我已经不再直接 prompt Claude 了,我的工作是写 loop。"框架 LoopX 把受控执行压成"决策→Agent 执行→独立验证器证明→LoopX 提交"——**模型可以提出"完成",但不能批准自己的"完成"**。循环失控三模式:token 成本失控、理解债(comprehension debt)、认知投降(cognitive surrender)

- **Agent 虚拟文件系统(数据平面)**:Agent 访问的不是单一存储,而是挂载到同一目录树的四类区域,通过统一 read_file/write_file/list_dir 接口访问(相当于 Agent 的地址空间,OS 保护哲学同样成立——默认隔离,共享须显式声明):
  - **Agent 专属工作区(Scratchpad)**:每实例独享私有目录,随实例销毁,对其他 Agent 和用户不可见。避免临时文件相互覆盖,保持主 Agent 上下文精简
  - **多 Agent 共享空间(Shared Workspace)**:多 Agent 共同读写、用户可见的协作区域,是交换产物的主要媒介。需持久化,是并发冲突高发处
  - **外部挂载资源**:用户授权的第三方信息源(Google Drive/Notion/Dropbox)经适配器映射为挂载点。访问受外部权限约束、延迟高一致性弱、多为只读
  - **系统内置资源**:系统预置对所有 Agent 只读共享的资源包(Skills、参考手册、模板库),全局共享、跨会话稳定

- **控制平面四项能力**(基于生命周期原语 spawn_subagent/send_message_to_subagent/cancel_subagent/list_agents,对应 fork/消息/kill/ps):
  - **消息传递**:点对点(拓扑固定、Agent 少)或经消息总线(多 Agent 异步并行,避免点对点连接数平方增长)。消息应携带结构化信封(发送者 ID、目标、消息类型、JSON 负载)
  - **状态查询**:最易被低估。拉取式 get_subagent_status 实际用处远小于预期(轮询两难:过密浪费 token、过疏不及时)。更自然的是回到两大通信范式——用消息传递(异步问答或子 Agent 到关键节点主动发布 status_update)或用共享文件系统(轨迹持久化为 JSONL 主 Agent 直接读,或约定 progress.md 轻量进度文件;进度文件最后修改时间超 N 分钟无变化即可判卡住触发超时兜底)
  - **执行终止**:优雅终止(graceful,首选,对应 SIGTERM——发信号→子 Agent 在安全点清理资源→ack→退出)vs 强制终止(forced,兜底,对应 SIGKILL,可能遗留悬挂资源)。级联终止有竞态——多 Agent 近乎同时上报成功,须用锁或幂等设计保证仅结算一次。残局借鉴 Go context——终止沿创建关系向下级联(取消一个 Agent 它派生的所有子 Agent 随之取消),杜绝孤儿 Agent
  - **资源与调度**:Agent 世界稀缺的是 token、资金和并发额度。启动子 Agent 时设定步数/token 预算超限即止;困难任务交强模型、机械任务交低成本模型;并发数设上限避免耗尽 API 配额

- **去中心化模式"由伪到真"递进线索**:刻意排成一条递进——**MetaGPT**(SOP 驱动,控制流其实是固定流水线=伪去中心化,但通信上靠"共享消息池 + 按角色订阅"实现解耦)→ **AutoGen group chat**(共享对话记录 + 中心化调度选择器的混合形态,介于共享与不共享之间)→ **OpenAI Swarm/Agents SDK**(真正在控制流上对等去中心化,每个 Agent 配备 handoff 选项可在任何时刻移交控制权,无中心调度者)。对等移交风险是成环(A→B→A 空转),需移交次数上限保护。看透概念本质:业界"Agent Swarm"有两类——OpenAI Swarm 式 handoff 网络(去中心化)vs 规模化管理者模式(Kimi K2.5 上百子 Agent 并行、Anthropic 多 Agent 研究、Manus Wide Research 的 orchestrator-worker 星型)

- **管理者模式关键结论**:把每个专门 Agent 建模为 Manager 可调用的工具("调用 Agent = 调用工具")。Plan-and-Act 论文实证——**弱规划者是整个系统最关键瓶颈**:Planner 分解有误,Executor 再强也建立在错误前提上。启示:最强模型和最精心提示词应给 Manager(规划者)而非平均分配。这与第 4 章提议/审核模型能力应相近不冲突——审查场景要求审查者跟得上被审者,规划场景要求规划者先对。形态分顺序协调(线性、清晰依赖)和并行协调(消息总线 + 实时监控 + 级联终止)

- **A2A 协议(跨组织协作)**:单机内 IPC 够用,跨组织边界(调用另一家公司的 Agent)就需标准化协议——A2A 之于 Agent 就是网络协议之于进程。2025 年 Google 发布(后捐赠 Linux 基金会)。三核心要素:**Agent Card**(能力元数据"名片",解决跨组织能力发现)、**任务生命周期管理**(状态机:已提交/进行中/需要输入/已完成/失败,原生支持长任务和流式进度)、**不透明协作**(只交换任务与产物,不暴露内部提示词/思考过程,与不共享上下文原则一致)。与 MCP 对照:MCP 解决 Agent↔工具,A2A 解决 Agent↔Agent;同团队内部用消息总线即可,跨信任边界才需 A2A

## Key Concepts

- **MAST 失败模式分类法**:2025 年《Why Do Multi-Agent LLM Systems Fail?》在 7 个主流框架上归纳的 14 种失败模式,分三大类——系统设计缺陷(接口定义不清、角色职责重叠)、Agent 间对齐失败(任务理解不一致、信息被误解、操作逻辑矛盾)、任务验证缺失(声称"已完成"但结果不符)
- **拜占庭故障 vs 崩溃故障**:传统系统只需防崩溃(部件停止工作);Agent 故障天生是拜占庭式的——不停工作但给看似可信的错误结论,且不主动声明。解释了为何修补单环节收效甚微:只能靠独立冗余(交叉验证、多数表决)发现。确定性外部反馈(测试/编译器/数据库查询)是系统里唯一不会说谎的部件
- **移交包(Handoff Package)**:不共享上下文下移交时显式决定传什么——任务描述(做什么、验收标准)、已确认的事实与约束、结构化产物的引用(文件路径而非内容)。刻意不传全量轨迹(试错/中间思考/失败尝试对接收方是噪声)
- **trajectory persistence(轨迹持久化)**:子 Agent 把轨迹实时序列化为 JSONL 日志(每会话一文件、每行一事件)。满足 WAL(预写日志)条件后可从最后确认状态恢复——需为工具状态、会话状态、外部副作用分别提供检查点与恢复契约
- **乐观锁(Optimistic Locking)**:每文件维护版本号/时间戳,读时记录版本,写时检查一致,不一致则失败重读。防丢失更新(lost update)。只防同文件写入冲突,跨文件语义冲突需更高层校验
- **工作副本隔离(worktree)**:多个 Coding Agent 并发改同一代码库的主流做法——每 Agent 独立 Git 分支/worktree,冲突推迟到合并点。对应 OS fork 的写时复制,与第 2 章"隔离优于压缩"同源
- **涌现行为(Emergent Behavior)**:系统整体表现出的、无法从单个个体规则直接预测的集体行为(如蚁群找最短路径)。Agent 数量跨过临界点后产生无法预先设计的集体行为
- **Agent 经济**:基于市场机制的协调方式——Agent 无需预先知道谁能完成任务,只需发布需求由市场撮合(Pinchwork 让 Agent 互相雇佣;RentAHuman 让 Agent 用加密货币雇佣人类执行物理任务)

## Mental Models

- **OS 类比贯穿全局**:Agent=进程、静态前缀=程序、轨迹=内存、LLM=分时复用 CPU、内核=Agent 运行时、系统调用=工具调用、fork=spawn_subagent、kill=cancel_subagent、ps=list_agents、退出码与 wait()=结构化摘要。换更快 CPU 程序照常跑;换更强模型 Agent 还是原来那个 Agent——身份和记忆在前缀与轨迹里,不在模型权重里。抽象可追溯到 1970 年代 Actor 模型,多 Agent 系统是其 LLM 版本。**唯一失效处**:进程传字节逐位保真,Agent 传语义每次转述可能失真
- **线程 vs 进程 = 共享上下文 vs 不共享上下文**;**共享内存 vs 消息传递 = 共享文件系统 vs 工具调用/消息总线**(Go 名言的取舍)。表 10-1 每条选择依据都能从这组 OS 取舍推出
- **把"完成"从宣称变成证明**:过早终止三态(偷懒式假完成/过早放弃/假成功)指向同一根源——验证之前"完成"只是模型的一句宣称。人的角色从"写提示词的操作者"变成"设计循环的工程师"
- **两朵乌云(后记点题)**:(1) Agent 如何流式实时与环境交互(turn-by-turn → 边听边想边说,靠快慢分离或把推理做快到 1000+ token/s);(2) Agent 如何从交互成败中持续积累经验(小世界假设 vs 大世界假设——前者认为大模型一次训练装得下通用知识,后者指出具体用户/公司的知识只能上岗后持续学习)
- **模型吃 Harness 一层层**:模型每稳定内化一种能力对应 Harness 层可删;但"吃"永不完结(训练以月计业务等不起、无法内化所有约束偏好、每代打开新前沿)。Harness 不消失,只随模型不断向新前沿迁移——这是《苦涩的教训》在 Agent 时代的读法。飞轮转最快处是同时握住模型与 harness 两端的人(不换模型只改 harness,准确率能从 52.8% 跳到 66.5%)

## Anti-patterns

- **过度协作 / 协作不引入新信息**:同模型自我审查、辩论同一段文本——等计算量下与单 Agent 持平甚至更差。Anthropic 披露多 Agent 研究系统 token 消耗约普通对话 15 倍,效果收益必须大到覆盖数倍开销,否则调校得当的单 Agent 更划算
- **上下文污染 / 错误级联放大**:共享上下文里前一个 Agent 的思维惯性影响后续判断(继承"需求分析师"上下文的"代码审查员"仍从需求角度思考)。更隐蔽的是错误级联放大:一个术语错误经三个 Agent 传播后因"一致性"获得更高可信度——校对看到全书统一用"推理"反而认为翻译质量高,实际把 reasoning 和 inference 两个不同概念合并了
- **死锁与活锁**:去中心化对等移交可能成环(A→B→A 空转);AutoGen group chat 可能发散——人人都在发言而整体不前进(活锁 livelock),需精心设计终止条件。级联终止有竞态——多 Agent 近乎同时上报成功,处理不当产生重复或矛盾状态
- **Manager 成为单点瓶颈**:Manager 必须理解所有子任务性质、选对 Agent、准确传上下文,任何决策偏差影响全局。弱规划者把任务分解错,后续所有 Executor 建立在错误前提上(Plan-and-Act:Planner 是最关键瓶颈)。Manager 上下文还可能随调用增多快速膨胀
- **拉取式状态查询**:get_subagent_status 轮询 PID 式状态实际用处远小于预期——轮询两难(过密浪费 token、过疏不及时),且 Agent 一经创建就执行到完成/失败,不像批处理作业在排队状态间流转
- **把 MetaGPT/AutoGen 当成"完全去中心化"**:MetaGPT 控制流是固定流水线只是通信解耦;AutoGen 有中心化 GroupChatManager 裁决发言者。需看清本质而非被标签误导
- **乐观锁误用**:只防同文件写入冲突,跨文件语义冲突(如 Agent A 重编全书图片编号、Agent B 同时引用原始编号)需更高层语义校验或编排层面避免有依赖文件被并行修改
- **轨迹持久化不完整就指望恢复**:仅持久化轨迹不够,包含外部系统(支付/预订/发消息等有副作用工具)的全部状态无法仅靠轨迹恢复。需持久化幂等键和规范化请求,恢复时先核对真实状态判定成功/失败/未知,未知结果只能在严格条件下重试否则交人工对账
- **循环失控三态**:token 成本失控、理解债、认知投降。解药同打断错误放大链——显式预算与终止条件、扎根真实观测的验证器、人始终保持"循环的工程师"角色

## Code Examples

**spawn_subagent 与结构化返回(管理者模式调用子 Agent,对应 fork + wait)**:

```python
# Manager 调用子 Agent = 调用工具(发请求 → 获响应)
# 子 Agent 应返回结构化摘要而非全量轨迹
result = spawn_subagent(
    agent="translation_agent",
    input={
        "chapter": "ch7.md",
        "glossary_ref": "/workspace/shared/glossary.json",  # 传路径不传内容
        "guide_ref": "/workspace/shared/translation_guide.md",
        "budget_steps": 40,
    },
)
# result 只含: 任务结论、关键发现、产物文件路径、遇到的问题
# 完整执行轨迹留在子 Agent 自己的 /scratch/<id>/trajectory.jsonl
# → Manager 上下文随子任务数线性增长,而非爆炸膨胀
```
- What it demonstrates: Manager 视角调用 Agent 等同调用工具;"只维护文件索引不保存翻译内容"是控制上下文膨胀的方法论。对应表 10-3 的 fork(创建)与退出码(wait)

**消息总线信封格式(并行协调,异步通信)**:

```json
{"type":"start","task":"采集 arxiv 论文","params":{"query":"LLM agent"}}     // Manager → Agent 1
{"type":"completed","agent_id":"3","result":"charts/fig1.svg 已生成"}          // Agent 3 → Manager
{"type":"data_ready","source":"agent_1","file":"raw_data.json"}                // Agent 1 → Agent 2(经总线,发送方无需知晓消费者)
{"type":"terminate","reason":"target_found_by_agent_3"}                        // 级联终止(一个成功,全员停止)
```
- What it demonstrates: 统一信封(发送者 ID、目标、类型、JSON 负载)保证可靠路由与解析,使协作链路可追溯——多 Agent 调试的关键。Redis Pub/Sub 轻量但不持久化;RabbitMQ 持久化但更重

**乐观锁(防共享文件丢失更新)**:

```python
config, version = read_file("config.json")   # version=3
# ... Agent B 在此期间改了同一文件,version 变 4 ...
ok = write_file("config.json", new_config, expected_version=3)
if not ok:  # 版本不一致,写入被拒
    config, version = read_file("config.json")  # 重读 version=4,基于最新版本重新修改再写
```
- What it demonstrates: 读时记录版本,写时检查一致,不一致则失败重读。代价是偶尔重试,换来一致性保证——Agent 永不基于过时状态决策。只防同文件冲突;跨文件语义冲突需 worktree 隔离或全局一致性检查

## Worked Example

**书籍翻译 Agent(实验 10-3,管理者模式控制上下文膨胀)**:翻译几百页技术书,单 Agent 面临严重上下文问题——术语表、已译章节、当前段落、翻译思考不断累积易超窗口;过长上下文中 Agent"迷失"(忘记术语约定、审校重复检查、幻觉出不存在的术语规则)。管理者模式通过任务分解和责任隔离解决:

- **Glossary Agent**:识别全书重复术语生成结构化术语对照表(JSON/CSV),写入 `/workspace/shared/glossary.json` 后即销毁释放资源
- **Translation Agent**(可并行多实例):接收当前章节 + 术语表 + 翻译指南,遇对照表术语严格用规定译法,遇新术语推断并标记待审;译文写 `chapter{n}_zh.md`,每实例独立上下文互不干扰
- **Proofreading Agent**:接收所有译文和术语表执行一致性检查,生成 `review_report.md`
- **Manager Agent**:上下文只保存任务描述、执行计划、各 Agent 调用记录和进度状态、**文件索引**——不保存完整翻译内容。据审校报告可把特定章节发回 Translation Agent 修订

关键优势是上下文隔离:每个 Agent 在精简专注上下文中工作,效率更高出错率更低。但此架构也暴露"错误级联放大"风险——若 Glossary 把 reasoning 译为"推理"(与 inference 歧义),后续 Translation 遇到 inference 也选"推理",Proofreading 看到全书"统一"反而认为质量高。这正是交叉验证与确定性外部反馈作为"断链器"的必要性。

**电话 + 电脑双 Agent(实验 10-4/10-5,并行协调 + 自主编排)**:填复杂航班预订表单需边操作网页边电话询问用户信息,两端都高实时性,单 Agent 顾此失彼。Phone Agent(ASR+LLM+TTS)与 Computer Agent(浏览器操作+Vision LLM)各自维护独立 ReAct 循环真正并行,通过 WebSocket 双向通信:`[FROM_PHONE_AGENT] 用户说姓名是张三` / `[FROM_COMPUTER_AGENT] 已填写姓名,需要证件号`。实验 10-5 更进一步:不是人预设流程,而是 Computer Use Agent 发现表单复杂且自己缺信息时**自主决策**调用 `initiate_phone_call_agent(purpose, required_info)` 启动 Phone Agent——这个决策写在其提示词里("当需要收集大量结构化信息且可通过对话逐步进行时,考虑调用 Phone Agent")。

## Key Takeaways

1. **两个正交维度决定一切**:上下文是否共享(线程 vs 进程)、协作拓扑如何组织(对等/管理者/去中心化)。两者概念独立、实践相关——共享上下文时拓扑多退化为角色切换序列,不共享时"信息如何流动、由谁协调"才成为必须显式设计的架构问题
2. **新信息是判断多 Agent 价值的唯一硬准则**:协作是否引入生成时不存在的新信息?自我审查、辩论同一段文本不引入,等计算量下不优于单 Agent;测试结果、渲染截图、工具验证才引入,显著提升。三种拓扑凡是真正有效的用法都能在这条判据上找到落点
3. **OS 类比是全书最深的脚手架**:Agent=进程、轨迹=内存、LLM=分时 CPU、fork=spawn_subagent。成熟经验大多可直接借用,唯一失效处是进程传字节逐位保真、Agent 传语义每次转述可能失真——这正是错误级联放大的根源
4. **数据平面 + 控制平面构成不共享上下文的基础设施**:共享文件系统(四类区域挂载的虚拟目录树)是数据平面;消息传递、状态查询、执行终止、资源调度是控制平面。三种拓扑本质上都是在这两个平面上对控制权归属与信息流向的不同选择
5. **把"完成"从宣称变成证明是 Loop 工程核心**:过早终止三态(偷懒式假完成/过早放弃/假成功)解药都是扎根真实观测的验证器。循环的瓶颈在验证器不在模型——模型可以提出"完成"但不能批准自己的"完成"
6. **最强模型给规划者,不是平均分配**:Plan-and-Act 实证弱规划者是系统最关键瓶颈。但审查场景相反——提议/审核模型能力应相近(审查者要跟得上被审者)。两个结论不冲突,切的是不同维度(规划-执行 vs 生成-验证)
7. **Agent 故障天生是拜占庭式的**:不停工作但给看似可信的错误结论,且不主动声明。解释了修补单环节收效甚微,只能靠独立冗余(交叉验证、多数表决)和确定性外部反馈(唯一不会说谎的部件)发现
8. **大规模 Agent 会涌现无法预先设计的集体行为**:社交涌现(AI 小镇 25 Agent 自发传播信息组织聚会)、长期生活(Agentopia 10 年模拟用"生活奖励"筛选轨迹训练模型,社会智慧可迁移)、经济涌现(Vending-Bench Arena 价格战与合谋定价、Pinchwork 市场雇佣、RentAHuman 雇人类执行物理任务)。暗示基于市场机制的去中心化资源分配这一新协调方向
9. **跨组织协作需 A2A 协议**:同团队内消息总线够用,跨信任边界才需 Agent Card + 任务生命周期状态机 + 不透明协作。MCP 解决 Agent↔工具,A2A 解决 Agent↔Agent
10. **模型与 Harness 共同演进是飞轮,也是护城河**:模型每内化一种能力对应 Harness 层可删;但"吃"永不完结。同时握住模型与 harness 两端的人飞轮转最快;应用层长久护城河往往在技术之外(数据、渠道、信任、网络效应)
