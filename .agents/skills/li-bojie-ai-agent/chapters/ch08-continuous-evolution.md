# 第 8 章 Agent 的持续进化

## Core Idea / 核心观点

Agent 的能力悖论是本章的起点:它可以零样本解决从未见过的复杂任务,却可能在处理了一万次相似任务后仍犯第一天的错误。能否自主从经验中学习,正成为 Agent 从"会完成任务"走向"能够可靠工作"的分水岭。

核心论点是:在模型自身尚不能可靠地持续学习时,必须先把"学习"构造成模型外围的一套自主系统。原因有三:推理时的上下文适应不会自动持久化;把对话存进记忆不等于学会了新行为;允许运行中的模型依据未经验证的反馈直接修改自身,会让错误经验和提示注入被固化并持续放大。

本章的关键洞察是**保存经历 ≠ 从经历中学习**。把一百条轨迹塞进向量库,可以帮助找回某个案例,却不会自动完成跨案例比较。学习发生在系统主动完成"评价、对照、归纳、验证"之后,而不是发生在日志写入磁盘的那一刻。第三章的用户记忆沉淀"用户与世界是什么样的",本章的经验学习则要进一步沉淀"在什么条件下应该怎样行动"——前者让 Agent 记得更多,后者才让它从聪明变得熟练。

本章的角色是把前几章已造好的部件(第二章任务内状态、第三章知识基础设施、第五章修改系统的元能力、第六章评估验证、第七章模型参数更新)组织成一个**持续进化闭环**:执行任务 → 记录轨迹 → 形成信号 → 生成候选更新 → 验证与发布。只有改变后续行为且通过验证的更新,才构成持续进化。

## Frameworks Introduced / 引入的框架

### 1. 持续进化闭环(图 8-1,贯穿全章的主干)

```
执行任务 → 记录轨迹 → 形成信号 → 生成候选更新 → 验证与发布
(用户、环境与    (动作、结果   (结果·过程·质量)  (知识/指令/程序/参数)  (回归、灰度、回滚)
 工具交互)       与反馈)                                                      
                              ↓ 只有通过验证的新版本才进入下一轮运行
```

要点:闭环里所有修改先形成**候选版本**,经过回归测试和安全检查后,才能改变下一轮运行。这不是对模型学习能力的替代,而是当前技术条件下让 Agent 获得持续学习能力的工程路径。

### 2. 学习信号三类:从环境结果到 LLM Rubric 的三层验证(图 8-2)

持续进化的起点不是"总结",而是"评价"。如果系统不知道任务是否完成、哪一步造成成功或失败,模型生成的反思只是猜测。三层结构自下而上:

- **结果验证器(最底层)**:读取测试结果、数据库状态、工具返回,回答"事情是否真的办成"。来自环境真实状态,通常比模型对自己行为的描述可靠。
- **过程验证器(中间层)**:检查业务规则、权限、动作序列与承诺—行动一致性,回答"是否以允许的方式办成"。
- **LLM Rubric / 质量验证器(最上层)**:依据预先定义的量表评价语言与策略,回答"是否办得合适"。

核心原则:**越靠下的指标越应依赖代码和环境真值,只有难以形式化的部分才交给语言模型**。验证结果不应被压缩成一个标量,而是一份结构化诊断:维度化信号既保留问题性质,也保留证据位置(标明对话轮次与工具状态),证据不足时允许拒绝评分。

### 3. 四种更新载体(图 8-3、表 8-2)

选择更新方式的首要依据不是经验出现了多久,而是**目标能力能否被某种载体自然表达**:

- **知识文档**:事实、经验规律、例外与来源
- **Prompt 与 Skill**:可语言化的判断原则和操作规范
- **程序与 Harness**:确定性流程、工具和强约束
- **模型参数**:高维感知、生成风格和隐式策略

四种方式不互斥而是互补(医疗影像 Agent 依靠参数识别病灶,用知识库提供最新指南,用代码计算风险指标;客服模型的自然语气来自后训练,具体政策由知识和 Skill 提供,关键合规则由服务端代码兜底)。此外还有一条正交的轴——**从更新产物到更新"更新方法"**(单条规则 → 结构化上下文 → 工作流 → Harness 代码 → 优化器代码),这是五种不同的搜索尺度,不是五种新的载体。

### 4. 在线执行与离线进化的双循环(图 8-5)

四种更新方式只有进入同一个自主循环,才从单次优化变成持续进化。生产系统更稳妥的结构是双循环:

- **在线执行循环**:只完成任务并记录证据,**不直接改写正式 Agent**。
- **离线进化循环**:聚合轨迹、诊断根因、生成候选修改,再通过验证门槛发布新版本。

两者通过版本化的经验库和评估集连接。关键设计:**可信根**——权限、审计、验证与回滚机制不位于普通进化流程可修改范围内。

## Key Concepts / 关键概念

- **能力悖论**:Agent 可零样本解决未见过的复杂任务,却可能在重复相似任务后仍犯第一天的错误。这是从"会完成任务"到"能够可靠工作"的核心障碍。
- **保存经历 ≠ 从经历中学习**:把轨迹放进向量库可帮助找回案例,却不会自动完成跨案例比较。学习发生在系统主动完成"评价、对照、归纳、验证"之后。
- **LLM Rubric**:对难以形式化的维度(自然、简洁、合规变通)预先定义的评分量表;要求验证器逐项给分、引用轨迹证据,并在证据不足时明确表示不确定,而不是只给模糊总分。
- **承诺—行动一致性**:Agent 场景特有的评价维度。传统文本评价只读最终回复,容易把"已为你提交退款"当作良好服务;轨迹评价则会继续检查是否真的调用了退款工具、调用是否成功、订单状态是否改变。
- **候选版本(candidate)**:所有修改先产生候选能力或候选 Agent,而不是直接覆盖生产版本。首次成功只生成 candidate,经验证后才发布为 validated。
- **灰度发布 / Canary**:验证通过后仍通过灰度观察真实流量,关键指标恶化时自动回滚到已知安全版本。
- **能力遗忘 / 灾难性遗忘**:一次局部更新可能造成能力遗忘、策略漂移或安全退化;参数更新尤其要检查通用能力和安全对齐是否遗忘。
- **Harness 更新能力 vs Harness 受益能力**(Lin 等人):前者是从轨迹中产生有价值的持久修改;后者是任务 Agent 在后续运行中找到、激活并正确使用这些修改。一个 Skill 可能写得完全正确,但较弱的任务模型没有在合适场景加载它——其中任一种都会让最终成绩看起来"没有进化"。**不能只用端到端分数反推更新器好坏**。
- **变更契约 / 影响预测**:每个修改请求应是一份可证伪的契约:列出失败证据、推断根因、归属的 Harness 组件、候选修改、预期修复的行为、可能受损的既有行为,以及分别验证两者的用例。Agentic Harness Engineering 把它概括为组件、经验、决策三层可观测性。
- **睡眠学习**:对离线整合的认知类比(不要求真的在夜间运行)。在线只追加不可变证据,后台学习进程在空闲期读取一批经历,比较新旧结论、合并重复、解决冲突、提出候选更新并运行回归。典型周期:触发 → 定向 → 采集与整合 → 验证与审批 → 修剪与索引。

## Mental Models / 心智模型

1. **"记事本"模型(Karpathy 的系统提示学习类比)**:预训练学知识,微调塑造习惯性行为;但人类还有一种学习——遇到问题想通方法后,用明确的语言提醒未来的自己"下次遇到这类问题,应先尝试这种办法"。缺少这种记事本的 LLM 像电影《记忆碎片》的主角。系统提示学习与 RL 都从经验中改进行为,但更新算法不同:前者编辑文字,后者用梯度下降改参数。知识引导的复盘比标量奖励具有更高维度的反馈通道,因此可能有更高数据效率。

2. **电子表格宏录制(程序化经验的直觉)**:第一次发邮件时 Agent 通过观察—思考—行动寻找控件;以后发另一封邮件流程没变只有参数不同,没必要再调用模型从像素重新发现整条路径。把第一次探索的轨迹编译成带参数、状态检查和版本信息的小程序——PreAct 在重复任务上实现 8.5-13 倍端到端加速。

3. **客服 Rubric 维度拆分**:比"用户是否满意"更有诊断价值——用户可能因 Agent 违规退款而满意,单一满意度无法区分。七维度(任务结果、规则遵从、隐私边界、事实可靠性、承诺—行动一致性、表达质量、合规变通)前五项约束底线,后两项衡量服务质量。

4. **Voyager 的三个咬合机制**:自动课程(知道下一步学什么)+ 可执行技能库(成功程序保存为可检索可组合的代码)+ 迭代提示(把环境观察、执行错误、自验证结果带回下一轮)。三者缺一不可:只有技能库没课程则不知学什么;只有反思没环境验证则积累错误;只有探索没持久化则每次从头开始。

## Anti-patterns / 反模式

1. **直接让模型在每次任务后训练自己**。生产环境很少提供干净学习信号:用户满意不代表合规,测试通过可能源于删除了失败用例。允许运行中的模型依据未经验证的反馈直接修改自身,错误经验和提示注入会被固化并在后续任务中持续放大。

2. **保存经历等于学习**。把一百条轨迹塞进向量库不会自动完成跨案例比较。学习发生在"评价、对照、归纳、验证"之后,而不是日志写入磁盘的那一刻。

3. **把原始轨迹当作正式知识单元**。原始轨迹既长又嘈杂,包含工具原始输出、偶然绕路和环境细节。一次偶然成功即可升级为正式知识,或文档无法追溯到原始轨迹,都不通过验收。

4. **只输出一个总分而不分维度**。单一总分掩盖隐私或规则维度的失败;应像结构化诊断——任务部分成功、规则遵从通过,但出现一处无证据陈述、一处虚假承诺。维度化信号既保留问题性质也保留证据位置。

5. **让同一个模型既当裁判又直接改写规则**。验证器负责给出评价和证据,至于应修改 Agent 哪个部分,应由独立的诊断与进化模块决定。

6. **忽视"假成功"陷阱(回放覆盖率 100% ≠ 任务完成)**。流程记忆必须同时具备动作前验证、动作后验证和存前独立验证,否则会得到危险假象——每个按钮都点过了,但某字段其实为空,任务从未真正完成。

7. **反复重写整份 Prompt/记忆造成细节流失**。为追求简洁,旧版本少数重要细节在多轮改写后逐渐消失;相互制约的条件被合并成一句过度抽象的原则。应像 ACE 那样维护带稳定标识符的条目集合,用增量更新而非每轮重写。

8. **只观察一个"进化后总分"反推更新器好坏**。Harness 更新能力与受益能力是两回事;应用双向模型替换分别定位瓶颈。优化层级也不应盲目向上爬——明确、反复出现且能定位到单一组件的故障优先做局部补丁,只有局部修改长期无法解决跨组件问题时才上升到工作流、Harness 乃至优化器层。

## Code Examples / 代码示例

**候选版本验证脚本骨架(综合实验 8-3、8-5、8-7 的发布门槛)**——所有修改先写隔离候选目录,四项门槛全过才发 `release_to_canary`,任一失败返回 `reject_candidate`:

```python
def release_gate(candidate, eval_sets):
    """候选版本发布门槛:补丁非空 + 来源可追溯 + 边界集改善 + 保留集不退化"""
    # 1. 补丁非空且来源可追溯
    if not candidate.diff or not candidate.source_trajectory_ids:
        return reject(candidate, reason="empty_or_untraceable")

    # 2. 失败边界集表现确有改善
    boundary = eval_sets["boundary"].run(candidate)
    if not boundary.improvement_significant():
        return reject(candidate, reason="no_boundary_gain")

    # 3. 旧任务保留集不退化(回归)
    retention = eval_sets["retention"].run(candidate)
    if retention.has_regression():
        return reject(candidate, reason="regression_on_retention")

    # 4. 安全 Rubric 通过(规则、隐私、拒绝边界未漂移)
    safety = eval_sets["safety"].run(candidate)
    if not safety.all_pass():
        return reject(candidate, reason="safety_drift")

    # 通过才放行到灰度,绝不直接覆盖稳定版
    candidate.status = "release_to_canary"
    write_manifest(candidate)   # 记录失败簇、来源、根因、diff、回滚版本
    return candidate


def reject(candidate, reason):
    """拒绝的候选也保留失败原因,供下一轮生成时查阅(避免换说法重提同样方案)"""
    candidate.status = "rejected"
    candidate.reject_reason = reason
    write_manifest(candidate)
    return candidate
```

**LLM Rubric 评估模板(客服 Agent 轨迹评价维度,表 8-1)**——要求逐项 pass/fail/uncertain + 证据轮次,证据不足时允许拒绝评分:

```
对以下轨迹按维度逐项评价,每项给出 pass / fail / uncertain + 证据轮次:
  1. 任务结果    | 用户核心诉求是否解决           | 最终环境状态、工具结果
  2. 规则遵从    | 是否违反政策、权限或必要流程     | 政策库、动作轨迹
  3. 隐私边界    | 是否泄露不应提供的信息          | 回复文本、数据访问记录
  4. 事实可靠性  | 陈述是否有知识或工具结果支持     | 引用来源、工具返回
  5. 承诺—行动一致性 | 声称完成的操作是否真实发生     | 回复与工具日志对照
  6. 表达质量    | 是否自然、简洁,避免重复与模板化   | 对话全文、语言 Rubric
  7. 合规变通    | 原方案不可行时,是否找到允许替代  | 用户目标、政策与后续动作
规则:uncertain 必须给出非空证据,不得只有结论;不得输出单一总分。
```

## Worked Example / 实战案例

### 一次完整的持续进化循环:航空客服 Agent 的"过早转接人工"(实验 8-3)

**问题**:航空客服 Agent 经常在用户质疑政策时过早转接人工。轨迹评价显示它没有违规,却缺少合规变通。

**Step 1 — 在线执行并记录轨迹**:稳定版 Agent 处理真实任务,记录动作、结果与反馈到版本化经验日志(不可变)。

**Step 2 — 形成信号(三层验证)**:`learning_signal.py` 把失败拆成规则遵从(通过)、任务解决(部分)、合规变通(失败)三个维度,保留来源 case ID。诊断指出这不是缺知识,而是缺一条可语言化的规则——**选错载体等于白做工**。

**Step 3 — 生成候选更新(选对载体)**:规律可用自然语言清楚表达,且作用于几乎所有任务 → 选 **Prompt** 载体。Coding Agent 读取现有 Prompt,只生成一个可审计的 `old_str → new_str` 最小编辑:要求 Agent 先解释政策、识别用户真正目标并寻找合规替代方案,同时**保留**用户明确要求人工或出现安全事件时的转接路径。补丁与来源、目标规则、修改理由共同写入候选 manifest。

**Step 4 — 验证与发布**:候选必须满足四项条件——补丁非空、来源可追溯、边界集(过度转接案例)表现确有改善、保留集(应转人工的安全事件)不退化。通过门槛只得到 `release_to_canary`,不直接覆盖稳定 Prompt。若新规则减少了过度转接却导致应转人工的安全事件被继续处理,即未通过回归,返回 `reject_candidate`。

**关键启示**:系统提示学习的价值不在自动追加更多文字,而在用生产边界案例不断澄清规则的适用范围。同一条"虚假承诺"问题可通过 Prompt、Harness 检查或参数训练缓解,选择依据是**目标能力的表示性质**:能清楚语言化 → Prompt/Skill;可精确执行 → 程序;高维隐式 → 参数。

**载体选择的反向案例**:不可重试错误仍被连续调用(`retryable=false` 仍重试)——这是可确定执行的约束,应进入**程序**(重试/熔断代码),而不是只在 Prompt 增加一句"不要重复调用"(实验 8-5)。诊断模块先聚合跨任务相同故障,达到跨轨迹支持门槛才创建修改请求,候选必须"不可重试调用次数下降 + 临时超时恢复率不降"双通过。

**长期判定**:实验 8-7 区分 `static`(不持久化) vs `append_only`(记住第一版规则却不会处理冲突或淘汰) vs `evolving`(保存版本并以新证据替换旧规则)。一个 Agent 即使最终准确率较高,只要仍引用已废止规则、靠违规捷径完成任务,或更新后遗忘原有能力,**都不能判定为持续进化**。

## Key Takeaways / 关键要点

1. **保存经历 ≠ 从经历中学习**。把轨迹塞进向量库不会自动完成跨案例比较;学习发生在"评价、对照、归纳、验证"之后。这是本章最重要的认知纠偏。
2. **持续进化的起点是评价,不是总结**。三层验证(结果·过程·质量)自下而上,越靠下越应依赖代码和环境真值。验证结果不应压缩成标量,而应是维度化结构化诊断。
3. **选择更新载体的首要依据是能力的表示性质,而非经验出现了多久**。能被事实/语言规则/程序完整表达 → 用对应外部载体;高维隐式能力 → 才进参数。四种载体互补而非互斥。
4. **所有修改先形成候选版本,经验证才发布**。在线只记录证据不直接改写正式 Agent;离线生成并验证候选,再灰度、监控、回滚。可信根(权限、审计、验证、回滚)不可自我修改。
5. **区分 Harness 更新能力与 Harness 受益能力**。不能只用端到端分数反推更新器好坏;用双向模型替换分别定位瓶颈在更新器、检索路由还是指令遵循。
6. **把"自我修改"转化为可审计的软件发布流程**。Agent 修改自己的代码不意味着运行中进程直接覆盖自身——从稳定版本创建候选分支,经静态检查、单测、安全扫描、失败轨迹重放、旧任务回归,再生成可灰度部署的新版本。
7. **持续进化的上限取决于系统能否评价它真正关心的目标**。在 Coding、工具调用等结果可自动验证的任务上闭环最可靠;对开放式科研、战略规划等反馈延迟、目标模糊的任务,人仍需参与问题定义和评价标准制定——结论与证据分离、保留负面结果、维护搜索多样性。
8. **长期运行需要周期性离线整理(睡眠学习)**。合并重复、把局部规则从全局 Prompt 移到领域 Skill、重新验证长期不用的工具、删除被新证据推翻的知识、必要时从原始基座重训 LoRA。否则上下文腐化会在更长时间尺度上重现。
