# Chapter 5: Coding Agent 与通用 Agent

## Core Idea
以开放任务为目标的通用 Agent,其核心是一个 **Coding Agent(能自主编写、修改和执行代码的 Agent)加上文件系统**——文件系统是存储代码、数据、记忆和中间结果的工作空间。这一判断来自工业界实践(从 Manus 到 OpenClaw):用少量通用工具(代码执行、文件读写、搜索)构建一个 Coding Agent 运行时,再叠加浏览器自动化、网络搜索等能力模块。代码生成之所以能担此重任,是因为它是一种**元能力(meta-capability)**——能在运行时动态创造出新的工具、约束和表达形式,而不必事先把所有能力预制好。

## Frameworks Introduced

- **Coding Agent 七个核心工具**(极简但完整):
  1. Code Interpreter(代码解释器):隔离沙盒执行 Python
  2. Bash Shell:终端执行命令(跑测试、处理特殊格式)
  3. 读文件 / 4. 写文件 / 5. 编辑文件(局部修改,代码迭代核心)
  6. Glob(文件名模式匹配,`**/*.py`) / 7. Grep(文件内容搜索)
  - When to use: 构建任何 Coding Agent 的最小起步集;主要覆盖第四章五分类中的感知和执行两类,协作/事件触发/用户沟通需另配

- **OpenClaw 架构范式**(Coding Agent + 文件系统 = 通用 Agent 核心):三层结构——多平台消息网关(WhatsApp/Telegram/iMessage/Slack/CLI)→ Coding Agent 运行时(七个工具 + Deep Research + Computer Use)→ 文件系统(记忆/知识/能力中枢)。文件系统中 MEMORY.md(用户偏好)、daily/YYYY-MM-DD.md(交互日志)、SOUL.md(Agent 身份与行为规则)、知识库文件、Git 版本控制。"大模型 = 新操作系统":屏蔽智能复杂性,提供统一抽象

- **文件系统作为中枢**(Markdown 而非向量数据库): 用户可直接打开文件阅读和修改 Agent 记忆(记错删一行即可),Markdown 天然保留时间顺序避免语义检索的时间混淆,可 Git 回滚。Agent 拥有写文件能力 = 具备修改自身外部产物的技术条件

- **Harness 四象限**(任务清晰度 × 验证自动化程度): 目标明确+可自动验证=最佳区域(有测试的 bug);目标明确+需人工验证=吞吐量受限(重构);目标模糊+可自动验证=高效地跑偏(linter 优化"代码质量");两者都缺=难以启动。Coding Agent 天然处于最佳象限——这是它成熟度最高的根本原因(软件工程几十年基础设施 = 现成 Harness)。Harness 在 Coding Agent 落地为四组件:验收基线(测试/CI)、执行边界(模块/权限)、反馈信号(Linter/类型检查)、回退手段(Git/沙盒/快照)

- **故障四层分类学**: API 层(限流/超时/截断)→ 工具层(幻觉调用/参数畸形/反复同错)→ 上下文层(窗口溢出/压缩失败/轨迹损坏)→ 控制流层(死循环/死亡螺旋)

- **错误恢复分级升级**(能用低级别就不升级): (1) 静默重试(指数退避+随机抖动,区分前台/后台调用);(2) 降级与接续(提升输出上限、追加元指令接续、降级备用模型);(3) 暴露给用户。工具层错误走另一路:不终止会话,把结构化错误喂回让模型自纠正。每条恢复路径都要有熔断上限(阈值来自产线数据,如压缩"连续 3 次"= 经验拐点)

- **元能力六方向**(由内向外,最终回到自身): (1) 思考工具——代码替代自然语言做严格推理;(2) 业务规则约束——把模糊政策编码为可执行校验;(3) 多媒体生成——代码生成 PPT/视频;(4) 系统适配器——代码连接异构 API,适配格式演化;(5) 生成式 UI——代码动态生成表单与界面;(6) Agent 自举——代码创造或修复新 Agent

- **提议者-审核者(Proposer-Reviewer)机制**: Proposer 生成代码,Reviewer 渲染截图用 Vision LLM 审查,迭代到达标或最大轮数。核心优势在上下文管理——Reviewer 只处理最新版本不受历史干扰。与第四章事前审批同源,差异在本章用于内容质量的多轮迭代

- **业务规则三重保障**: (1) 系统提示词自然语言规则(理解/解释)→(2) 工具描述 + expected_* 参数作 checklist(引导调用前核对)→(3) 服务端基于数据库真值的代码化校验(守门员)。前两重减少错误,第三重确保不变成不可逆损失

- **Artifact 模式**: Agent 只生成代码不参与数据传递——数据从数据库直达前端绕过 LLM。生成代码不能直接执行:只读账号、只允许批准的 SELECT、参数化绑定、限制时间/行数/表

- **信任边界下移到数据层**: 动态生成的业务代码层不稳定(可能漏权限检查),不可违反的约束应留在稳定的、经人类审查的数据层(行级安全策略、受控视图、受信任运行时绑定的 access context)

## Key Concepts

- **元能力(meta-capability)**: "能创造其他能力"的能力;代码生成精确、可执行、可组合,既能产出新工具也能产出新约束和新表达
- **自举(bootstrapping)**: Agent 用代码创造或修复另一个 Agent,类比 DNA 自复制但理解自身机制、可定向修改
- **致命三要素(Simon Willison)**: 访问私有数据 + 暴露于不受信任内容 + 具备外部通信能力;作者补充第四维——**持久记忆**(攻击放大器,跨会话潜伏)
- **死亡螺旋**: 错误路径触发的恢复逻辑自身又调用 LLM,再次出错连锁触发(如停止钩子生成 commit message 再次溢出)
- **委托方忠诚(principal loyalty)**: Agent 在多方委托中"站在谁那一边";默认"谁说话帮谁"是危险设置,提示注入本质是一次策反
- **生成式 UI / A2UI**: Agent 动态生成表单/图表/Web 应用;A2UI 让 Agent 只输出界面描述清单(JSON),客户端用预定义安全组件渲染(餐厅菜单比喻)
- **内科指标**: 反映训练过程本身是否正常的内部信号(损失/梯度/perplexity/KL 散度),比结果准确率更早暴露问题

## Mental Models

- **Coding Agent = 最成熟的 Agent 类型**: 不是因为代码模型特别强,而是软件工程基础设施(测试/类型系统/Git)天然构成强大 Harness
- **代码即证明**: 一段能跑通的代码本身就是逻辑自洽的证明,执行结果提供客观对错标准——自然语言做不到
- **Agent 可靠性 = 每类故障都有对应的检测/恢复/终止路径**: 不取决于犯不犯错,而取决于边界条件下的鲁棒性
- **模型与脚手架此消彼长**: 模型够强时脚手架可更薄(增益收窄);评估脚手架效果必须考虑模型能力边界——同一套脚手架配不同模型结论可能截然相反
- **约束优先于指导**: 能用代码强制的规则就不要用文档建议——Linter/类型约束/CI 是"做不了",系统提示词"请遵循"只是"建议别做"
- **远程友好的团队也对 AI 友好**: 评估"AI-ready"的代理指标——远程新人只靠仓库和文档能否独立开展工作

## Anti-patterns

- **把代码生成只当"写程序"**: 它是通用问题解决手段(数学推理/规则固化/临时造工具/动态解析)
- **验收基线只管结果不管过程**: 修数据库故障直接删库重建"修复"生效但数据没了。生产级 Harness 必须对 rm -rf、删生产数据、覆盖未读文件等危险动作设专门检查(约束动作而非仅结果)
- **关键字黑名单做命令安全**: Shell 组合爆炸让黑名单形同虚设(`$(echo rm) -rf /` 绕过;`find / -name '*.log' -exec rm {} \;` 嵌套危险)。必须语义解析,理解参数消费规则
- **笼统地"出错就重试"**: 不可重试错误(参数不合法/权限不足/工具不存在)重试多少次都同样结果。必须维护错误→恢复策略映射表
- **信任模型自报参数作守门员**: 把 cabin_class/current_time 设计成模型填写的参数,模型报错一个值守门员就形同虚设。最后一道防线必须建立在模型无法伪造的数据上(服务端真值+服务端时钟)
- **让 LLM 读数千行数据再复述**(传统 SQL 模式): 抄写易错、消耗 token、延迟高。应用 Artifact 模式让数据直达前端
- **把权限检查放在动态生成的业务逻辑里**: 它与被约束代码同处一个信任域。信任边界必须下移到稳定的数据层
- **错误路径上调用会再次触发模型的副作用逻辑**: 停止钩子在溢出时又调 LLM → 死亡螺旋。错误路径应禁用副作用逻辑 + 用递归深度计数器打断连锁

## Code Examples

**ReAct 循环里七工具协作的极简轨迹**(整理项目 TODO 注释):

```
Agent(思考): 需要找到所有包含 TODO 的代码行。
Agent → Grep("TODO", glob="**/*.py")          # 搜索文件内容
工具返回:
    src/api.py:42: # TODO: add rate limiting
    src/db.py:15:   # TODO: migrate to PostgreSQL

Agent(思考): 找到 TODO,整理成清单写入文件。
Agent → Write("TODO_LIST.md", content="...")   # 写文件

Agent: 已整理完毕,清单保存在 TODO_LIST.md。
```
- **What it demonstrates**: 只用 Grep + Write 两个工具;复杂任务(统计并画柱状图)再加 Code Interpreter 跑 Python。七工具组合即可覆盖极多样化任务

**业务规则代码化校验**(服务端真值守门,expected_* 仅作 checklist):

```python
def cancel_reservation(reservation_id, cancellation_reason,
                       expected_cabin_class=None, expected_has_insurance=None):
    # 所有政策事实一律从数据库读取,绝不采信模型自报
    r = db.get_reservation(reservation_id)
    now = server_clock.now()             # 服务端时钟,而非模型提供
    # 模型自报值与真值不一致时记录告警(发现错误认知或潜在注入)
    if expected_cabin_class is not None and expected_cabin_class != r.cabin_class:
        log_mismatch(reservation_id, "cabin_class", expected_cabin_class, r.cabin_class)
    if r.any_segment_used:
        return {"success": False, "reason": "Cannot cancel with used segments"}
    # ... 其余规则逐条以 r.* 和 now 判定
```
- **What it demonstrates**: 独立性不仅指独立的模型,更指独立的数据来源;expected_* 引导模型调用前逐条核对(填参数=强制 checklist),但服务端从不把它当事实

## Reference Tables

**Coding Agent 七个核心工具**:

| 工具 | 作用 | 典型用例 |
|---|---|---|
| Code Interpreter | 沙盒执行 Python | 数据分析、统计绘图、符号计算 |
| Bash Shell | 终端执行命令 | 跑测试、处理特殊格式文件 |
| 读文件 | 读代码/配置/日志 | 理解项目、定位问题 |
| 写文件 | 创建或完全重写文件 | 生成新模块、产出报告 |
| 编辑文件 | 局部修改现有文件 | 代码迭代核心操作 |
| Glob | 文件名模式匹配 | `**/*.py` 探索项目结构 |
| Grep | 文件内容搜索 | 定位函数调用、错误消息 |

**四种文件编辑方案对比**:

| 方案 | 机制 | 代表/现状 |
|---|---|---|
| 差异描述 + Apply Model | 生成 diff/骨架,小模型合并 | Cursor 早期(基模增强后已弃) |
| Old String → New String | 字符串查找替换,存在且唯一则成功 | Claude Code、Codex、当今 Cursor |
| 行号定位 | 删第 X-Y 行插入新内容 | 行号精确但多次编辑需用初始行号 |
| 字符串首尾匹配 | 只给开头和结尾几行定位中间 | 综合可靠性与效率,风险较低 |

**四类搜索工具**(从粗到细、从语义到语法): grep/ripgrep(正则内容,不理解语义)、glob(文件名,最快,探索结构第一步)、语义搜索(向量+BM25+reranker;Claude Code 刻意不建索引避免陈旧+数据外发风险,Cursor 愿付成本)、符号定义/引用(LSP,区分同名符号,重构必备)

## Worked Example

**OpenClaw 执行轨迹**(分析上季度销售数据并生成报告):
1. 读记忆:Agent 读 MEMORY.md,发现用户偏好 PDF,数据源是 Google Sheets
2. 调工具:网络搜索获取 Sheets API 用法,代码执行下载数据
3. 写代码:Python 生成分析脚本(pandas 聚合、matplotlib 可视化)
4. 生成产物:结果写入 report.pdf,图表写入 charts/
5. 更新记忆:在 MEMORY.md 记录"User's sales data is in Google Sheets, ID: xxx",下次无需再问

整个过程中文件系统是信息流转的枢纽——记忆从文件读取,产物写入文件,经验也保存为文件。OpenClaw 全权限本地 Agent 四类边界(数据/输入信任/输出影响/跨会话)兼备,安全防护因此成为此类 Agent 的核心挑战。

## Key Takeaways

1. **Coding Agent + 文件系统 = 开放任务型通用 Agent 的核心技术基础**: 主要适用于任务边界不确定、产物形态多样的场景;垂直客服 Agent 以固定业务流程为核心,但 coding 仍是所有 Agent 的共同底线
2. **七个核心工具构成完整但极简的工具箱**: 不是第四章五分类的子集,是 Coding Agent 特有基础配置
3. **代码生成是元能力而非普通工具**: 六方向由内向外(思考→规则→内容→接口→界面→自身),最终回到 Agent 自举
4. **Coding Agent 成熟度最高归功于软件工程基础设施**: 不是因为代码模型特别强
5. **Agent 可靠性 = 每类故障都有检测/恢复/终止路径**: 检测靠"错误分类+模式识别",恢复靠"分级升级",终止靠"熔断器+全局上限+人工升级"
6. **模型与脚手架此消彼长**: 弱模型上增益显著的方案换强模型可能收敛到零
7. **业务规则三重保障**: 最后一道防线必须建立在模型无法伪造的数据上
8. **Artifact 模式让数据绕过 LLM**: Agent 只生成代码,系统执行代码;执行层仍需只读账号/SELECT 白名单/沙盒
9. **动态生成软件要把信任边界下移到数据层**: 应用层可变,数据层稳定;即使 AI 写错权限检查,数据层仍拒绝越权
10. **致命三要素 + 持久记忆**: 委托方忠诚要求主人指令优先级最高、外部内容默认降格为"可参考但无指令效力"
