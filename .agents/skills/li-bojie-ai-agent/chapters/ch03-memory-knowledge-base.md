# Chapter 3: 用户记忆和知识库

## Core Idea
持久化记忆体系在两个尺度上解决同一问题——让 Agent 在对话结束后仍"记得"。用户记忆(个体尺度)让 Agent 成为"懂你的助手",知识库(群体尺度)让 Agent 成为"领域专家";两者共用向量检索、知识压缩等底层技术,也同受信息冲突、知识过期、检索不准之苦,最终汇合于**双层记忆架构**:Advanced JSON Cards 常驻概览 + 上下文感知检索按需取细节。

## Frameworks Introduced

- **记忆能力三层次评估框架**(贯穿全章的标尺,实验 3-1/3-9/3-11 都用它度量):
  - 第一层 基础回忆:准确存取无歧义事实("会员号 12345")
  - 第二层 多会话检索:跨对象、跨时期会话中检索全部相关信息并推理(两辆车、有效合同、复合事件)
  - 第三层 主动服务:综合久远记忆发现深层联系,无明确指令下主动预警与整合(护照过期预警、报税待办清单)——试金石
  - When to use: 评估任何记忆系统前先立标尺

- **记忆设计三套正交分类**(表 3-1,避免混淆的关键;三套维度可自由组合):记忆层次回答"放哪里"(轨迹/长期记忆/业务状态),存储格式回答"怎么存"(四种格式),认知类型回答"存什么"(情景/语义/程序)

- **四种存储格式光谱**(简单性递减、表达力递增):Simple Notes(原子事实,O(1),关联丢失)→ Enhanced Notes(整段叙事,冗余难更新)→ JSON Cards(三层嵌套,部分更新,刚性分类)→ Advanced JSON Cards(加 backstory/person/relationship/时间戳,原生消歧,成本高)。When to use: 关键少量数据用 Advanced JSON Cards,大量非关键事实用 Simple Notes,多数生产系统走混合模式

- **混合检索三阶段流水线**(生产级 RAG 默认配置):
  1. 并行检索:稠密(语义)+ 稀疏(BM25)各召回候选
  2. 结果融合:加权归一化或 RRF(倒数排名融合,得分=Σ 1/(k+rank),k 常取 60)
  3. 神经重排序:跨编码器对 Top-N(如前 50)精排(如 bge-reranker-v2-m3)
  - 关键澄清:重排序不是"补救 RRF 丢分",而是换用更强的匹配范式;融合产生候选池,重排序在池上精排

- **知识更新双路径**(缺一不可):增量更新(事件触发)把知识库当代码库、每次变更当 PR,Proposer 提交小而完整 diff、异源 Reviewer 结合原始证据独立审核、迭代至收敛后合并并重建派生索引;定期整理(周期触发)做去重去旧合并、回到原始数据核查、冲突解决与场景限定(qualification),产物仍走 PR 不直接覆盖主库。Proposer 与 Reviewer 必须用不同家族、能力相近的模型(异源互审)

- **双层记忆架构**(本章两条线索的汇合点,主动服务的工程落地):Advanced JSON Cards 常驻上下文提供"概览",上下文感知检索按需提供"细节";只靠常驻会因容量受限丢细节,只靠检索会因缺乏全局视野发现不了跨会话隐藏关联,两者叠加才落地"主动服务"

## Key Concepts

- **用户记忆(User Memory)**: 主动的、持续的学习过程,目标是构建关于用户的简洁有效的预测模型;持久、可审查,区别于临时性的上下文学习
- **轨迹(Trajectory)**: 一次 Agent 运行的完整 append-only 事件记录,只增不改,对应"动态轨迹"
- **User as Code**: 把记忆介质从文本换成可执行 Python,带类型 dataclass 保存状态、函数编码约束;"表示用户"与"推理用户"在同一可运行介质中发生(预写日志 + 周期检查点的经典 DB 设计首次用于 LLM 记忆)
- **RAG(检索增强生成)**: 检索器从知识库找相关片段,生成器拿片段作上下文生成答案;让 LLM 利用训练时没见过的知识而无需重训
- **稠密嵌入(Dense Embedding)**: 深度学习把文本映射到向量空间,语义相近则向量方向相近,用余弦相似度衡量;从 Word2Vec 静态词向量演进到 BERT/BGE-M3 上下文感知
- **稀疏嵌入/BM25**: 极高维向量,多数维度为零;TF-IDF 加词频饱和(k1)与长度归一化(b),精确关键词匹配但读不懂同义词
- **倒排索引(Inverted Index)**: 从词反向映射到包含它的文档,如同书后术语索引页
- **上下文感知检索(Contextual Retrieval)**: 索引前先用 LLM 给每个文本块生成简短上下文前缀再拼接索引;Anthropic 数据显示检索失败率降 49%(+BM25)、67%(+重排序)
- **智能体化 RAG(Agentic RAG)**: 把检索封装成工具,Agent 用 ReAct 循环自主决定查询关键词、评估信息充分性、迭代搜索直至掌握足够材料
- **结构化索引**: 索引前先用 LLM 归纳抽象建立关联;RAPTOR 自下而上递归抽象建树,GraphRAG 用实体-关系三元组建图
- **实体消歧(Entity Disambiguation)**: 区分现实中两个同名实体(两位"张医生"),靠图结构的关系边原生区分;区别于靠上下文嵌入解决的词义消歧

## Mental Models

- **用数据库"预写日志 + 周期检查点"当 LLM 记忆更新模型**: User as Code 的记忆阶段是只增日志(不丢事实),结构化阶段是周期检查点(压缩成可查询结构)
- **遇到"100 个案例求比例"时用预提炼摘要替代原始检索**: 注意力是软检索、统计需预先提炼;把"100 个个体案例"压缩为统计摘要,把"三个孤立案例"提炼为明确规则,一次检索即获准确信息
- **用"猎头初筛 + 面试官深谈"当双编码器 vs 跨编码器**: 双编码器各自编码再算相似度(快但浅,大规模初筛);跨编码器把查询与文档拼接逐词比对(慢但准,精排)
- **遇到"该公司收入增长 3%"这种孤立块时用上下文前缀重新锚定**: 分块切断指代与出处,索引前补一段"[ACME 公司 2025 Q2 财报·关键业绩指标]"前缀,同时增强稀疏与稠密两路检索
- **用 Wikipedia 的交叉链接当文件系统知识库的组织范式**: 每个条目提及时以链接回指,辅以入口页与索引页;否则知识越多越像互不相连的孤岛

## Anti-patterns

- **把原始案例直接平铺进知识库**: 黑猫白猫计数问题受 top-k 截断、检索分数参差、跨文档聚合错位三重打击;Xfinity 优惠案例因检索器只召回语义相近的"医生"案例而错误推断护士可享。必须索引阶段提炼摘要或规则
- **把记忆冲突处理只放在写入阶段(Mem0 v2 路线)**: 一次错误的 UPDATE/DELETE 不可逆丢失历史,且每条候选事实都要经历检索和第二次 LLM 判断;Mem0 v3 改为 ADD-only + 混合检索 + 时间排序
- **Proposer 与 Reviewer 用同家族模型或只看挑好的片段**: 同族偏好相近易犯同类错误;Reviewer 没有完整证据库与工具权限就只能沿 Proposer 结论复述
- **文件系统范式下任由知识退化成互不相连的孤岛**: 不少模型不会主动回指已有条目、维护索引;写入提示词必须明确要求每新增条目先检索并链接相关已有条目、更新目录索引页,形成双向可达引用网络
- **只做定期重写不做增量更新(或反之)**: 只更不理越积越乱;只定期重写新信息无法及时生效。两条路径必须并存
- **让检索内容直接触发高风险操作**: 检索文档是间接提示注入最典型的载体;转账/删除/对外发信等副作用动作须独立授权,不能仅凭检索内容自动执行

## Code Examples

**User as Code:把记忆建成可执行代码后,聚合/冲突/约束都变成确定性函数**(本章最具教学价值的范式转变):

```python
from datetime import date

# 结构化阶段:带类型的状态
passport = PassportInfo(
    number="AB1234567", country="US",
    expiry_date=date(2025, 2, 18),
)
trips = [
    Trip(destination="Tokyo", departure_date=date(2025, 1, 15),
         is_international=True),
]

# 其一:聚合统计——文本记忆要逐条数,这里是一行表达式
>>> sum(1 for t in trips
...     if t.is_international and t.departure_date.year == 2025)
2

# 其二:冲突发现——用药与过敏按药物类别交叉比对
def check_drug_allergy(profile):
    for med in profile.current_medications:
        for allergy in profile.allergies:
            if med.drug_class == allergy.drug_class:
                yield (f"用药冲突:{med.name} 属于 {med.drug_class} 类,"
                       f"而患者对 {allergy.allergen} 严重过敏")

# 其三:约束执行——状态更新时自动触发,无需用户开口
def check():
    for trip in trips:
        if trip.is_international:
            days = (passport.expiry_date - trip.departure_date).days
            if days < 180:
                yield (f"护照 {passport.expiry_date} 到期,距 {trip.destination}"
                       f"行程仅剩 {days} 天,请尽快续办")
```

- **What it demonstrates**: 把介质从文本换成可执行代码后,原本只能靠 LLM "读一遍再心算"的聚合、冲突发现、约束执行都变成确定性的代码,正确率接近 100%

## Reference Tables

**ANNOY vs HNSW 索引算法对比**(表 3-2):

| 特性 | ANNOY(基于树) | HNSW(基于图) |
|---|---|---|
| 构建速度 / 内存 | 快 / 低 | 较慢 / 较高 |
| 增量更新 | 不支持(需完全重建) | 支持(长期插入后建议定期重建) |
| 查询精度 | 较高 | 极高 |
| 适用场景 | 静态数据集 | 需要实时索引的动态场景 |

**检索质量三个核心指标**(表 3-3):

| 指标 | 直觉解释 |
|---|---|
| recall@k(命中率口径) | 正确答案文档出现在前 k 个结果中的查询比例——"该找的找到了吗",最贴近 RAG 需求 |
| MRR | 每查询取第一个相关文档排名的倒数再平均——"找到得够不够靠前"(排第 1 得 1 分,排第 10 得 0.1) |
| nDCG | 综合所有相关文档排名与相关程度,排名越靠后折扣越大——"整个排序列表质量如何" |

**RAPTOR vs GraphRAG**(实验 3-7):

| 维度 | RAPTOR | GraphRAG |
|---|---|---|
| 结构 | 树状层次(叶子→聚类摘要→根) | 实体-关系三元组图谱 |
| 检索路径 | 跨层穿梭:宏观概念→向下钻取细节 | 关系网中漫游:定位实体→遍历关系边 |
| 擅长查询 | "从概念逐步钻进细节" | 多跳推理、实体消歧、"A 和 B 什么关系" |
| 代价 | 索引与查询都需多次 LLM 调用 | 同上;三元组提取导致语义降级(条件逻辑丢失) |

**何时需要结构化索引**:找包含某信息的文档片段("退款政策")混合检索即可;跨文档综合("SSE 与 AVX 架构区别")才值得结构化索引。

## Worked Example

**实验 3-11 ★★★ 双层记忆架构解决第三层"主动服务"**(layer3/01_travel_coordination.yaml):用户即将赴东京,护照 2025-02-18 过期,机票在一月。

单独用任一种技术都不够:只用 Advanced JSON Cards 常驻上下文能掌握"东京之行"与"护照过期"两个核心事实但缺机票具体日期;只用上下文感知检索能取回原始对话但缺全局视野,发现不了跨会话隐藏关联。

双层协同:① 事实回顾(审视 JSON Cards)→ ② 关联推理(发现机票日期一月与护照过期二月接近)→ ③ 细节验证(RAG 查找护照与东京机票相关原始对话)→ ④ 主动服务("护照即将过期,强烈建议加急续签")。

对照实验 3-9 的失败:仅用对话分块索引(无上下文前缀)时,layer2/12_contradictory_financial_instructions.yaml 中妻子设立转账、丈夫改金额日期、妻子又改回来,系统看到三个孤立矛盾的转账指令无法判断最终有效性;加上下文前缀后([妻子 Patricia 设立初始电汇]、[丈夫修改之前电汇]、[妻子在丈夫修改后再次修改]),时间/人物/意图线索让 Agent 能判断指令优先级。

**量化数据**:Anthropic 上下文感知检索使检索失败率(1 − recall@20)降 49%(+BM25)、67%(+重排序),索引阶段额外 LLM 调用通过 prompt caching 摊薄(每百万文档 token 约 1 美元)。Mem0 v2→v3(冲突处理从写入期移到检索期)LoCoMo 71.4→92.5(+21.1),LongMemEval 67.8→94.4(+26.6)。

## Key Takeaways

1. **先立评估标尺再设计**:三层次框架(基础回忆→多会话检索→主动服务)贯穿全章;最高层要求系统同时握有全局概览与精确细节,是试金石
2. **记忆设计三套分类是正交维度**:层次(放哪里)、格式(怎么存)、认知类型(存什么)可自由组合,别混为一谈
3. **存储格式走混合模式**:关键少量数据用 Advanced JSON Cards 保证可检索性,大量非关键事实用 Simple Notes 降成本
4. **生产级 RAG 默认走三阶段混合检索**:稠密+稀疏并行召回 → RRF/归一化融合 → 跨编码器精排;没有单一检索策略在所有场景可靠
5. **用 User as Code 把"心算"变确定性代码**:聚合、冲突发现、约束执行在文本记忆里靠 LLM 易错,换成带类型 Python 后正确率接近 100%
6. **上下文感知检索是回报率极高的索引期投资**:给每个分块补 LLM 前缀,检索失败率腰斩;与第二章"上下文感知压缩"划清界限——索引期做加法补背景 vs 运行期做减法去冗余
7. **知识更新必须双路径并存**:增量更新及时吸收新证据,定期整理回到原始数据全量重审;都走 Proposer-Reviewer 异源审核 + PR 流程,索引是可重建的派生物,Git 中已审核知识才是来源
8. **双层记忆架构是收敛结论**:Advanced JSON Cards 常驻概览 + 上下文感知检索按需取细节,才让"主动服务"在工程上落地
9. **把知识库当可读写代码库而非只读仓库**:从结构化数据(如司法判例)自下而上提取因子、建模重要性层级,是从"信息检索"到"知识发现"的飞跃
