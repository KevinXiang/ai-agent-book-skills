# Chapter 6: Agent 的评估

## Core Idea
评估的对象**不是模型,而是模型 + Harness 的组合体**。同一个模型在不同 Harness 里可能差异悬殊,因此当 Agent 表现不佳时,改进方向未必是换模型,而是优化 Harness(提示词、工具设计、反馈循环)。评估体系的首要价值不是给当前系统打分,而是**让你能快速、可靠地跟上模型的演进**——拥有完善评估体系的团队能在数小时内得出切换决策,缺乏评估的团队只能凭直觉。评估在 Harness 中扮演"验证"功能的核心角色,贯穿全章的方法论是:**观察 → 假设 → 实验 → 验证 → 新认识**,把 Agent 工程从"炼金术"推向数据驱动的科学工程。

## Frameworks Introduced

- **评估体系三层次**(全章骨架):
  - 第一层 **评估环境**("在哪里测"):工具调用型(Verifiers)、人机交互型(τ-bench / τ²-bench)、仿真环境
  - 第二层 **评估方法**("怎么判"):数据集设计、评估指标体系、LLM-as-a-Judge、配对比较与排名
  - 第三层 **评估驱动决策**("测了干什么"):模型选型、架构优化、持续迭代、统计显著性
  - When to use: 构建任何 Agent 评估体系时按此顺序思考

- **评估环境五要素**: 数据集(任务集合) + 环境状态(可变信息) + 工具接口(原子操作集合) + 评分标准(Rubric) + 执行协议(交互模式与终止条件)
  - 关键: 工具不应提供过高层抽象(如"解决用户问题"),而应提供原子操作,迫使 Agent 通过规划来组合

- **两种评估范式对比**:
  - **工具调用型(Verifiers)**: 基于可执行验证器(test pass/答案匹配),无需人工/LLM 评判;层次化环境(SingleTurnEnv / ToolEnv / StatefulToolEnv / SandboxEnv)
  - **人机交互型(τ-bench / τ²-bench)**: 用户模拟器(LLM 扮演用户)+ 双重验证(DB 状态检查 + 对话内容关键词搜索)
  - 根本区别: 前者考察"行动正确性",后者考察"沟通策略合理性"

- **渐进式信息透露(Progressive Information Disclosure)**: 人机交互型评估与传统 benchmark 的根本区别。绝不能一开始就把模拟用户的所有信息暴露给 Agent,信息按需、渐进地在对话中透露——用户往往只会说"我的航班好像有问题",Agent 主动提问澄清本身就是能力体现

- **model swap(模型替换实验)**: 固定 Harness,只更换更强/更弱的模型,观察分数变化幅度
  - 换强模型分数不涨 → 瓶颈在 Harness
  - 换弱模型分数大跌、分数随模型能力大幅波动 → 瓶颈在模型能力本身
  - When to use: 区分"模型能力不足" vs "Harness 设计缺陷"

- **消融实验(Ablation Study) vs model swap**: 两种正交方法,容易混淆
  - 消融: 关闭 Harness 的某个组件看整体性能如何变化 → 定位 Harness 内部哪个部件重要
  - model swap: 固定 Harness 只换模型 → 区分瓶颈在模型还是在 Harness
  - 前者横向(Harness 内部),后者纵向(模型 vs Harness)

- **LLM-as-a-Judge**: 用 LLM 充当评委,根据专家定义的 Rubric 自动化评判开放式任务输出
  - 必须先在人工金标集(100-200 案例)上校准(kappa > 0.7),否则只是"另一个模型的意见"
  - **多源异构评判**: Agent 用 Claude 则评判用 GPT-5 + Gemini,不同家族偏见正交,难同时欺骗

- **Rubric 四准则**(Scale AI "Rubrics as Rewards"):
  1. 基于专家指导(反映领域知识)
  2. 全面覆盖(事实/逻辑/完整性/安全性 + 明确 Pitfall 陷阱)
  3. 标准重要性权重(Essential / Important / Optional / Veto),支持一票否决
  4. 自包含评估(每个评价项独立可操作,不依赖评价者领域知识)
  - Rubric 是迭代产物,逐渐从抽象准则演化为详尽判例集

- **评估指标体系**(指标词典):
  - 过程指标: 行动合法率、工具调用正确率、路径效率(步数/冗余/回退)、检索覆盖率、成本与延迟
  - 结果指标: 任务成功率、Pass@k(能力上限)、Pass^k(稳定性)、Best@k(质量上限)
  - 安全合规指标: 零容忍原则,一次严重违规即否决
  - 鲁棒性: 随机种子敏感性、页面变化适应性、API 抖动容忍度

- **评估驱动决策闭环**: 评估环境 → 数据集 → 自动化评估(LLM-as-a-Judge + Rubric) → Benchmark 分析 → 系统改进 → 更新评估集 → 新一轮迭代

- **内部评估基础设施五组件**(生产级 Agent,OpenClaw 案例):
  1. 消融基础设施(总开关创造"裸模型"基线)
  2. AB 测试方法论(多臂而非二元、区分机制指标与目标指标、护栏指标)
  3. 双层特性开关系统(编译时移除 + 运行时下发)
  4. 提示词敏感性评估(可确定性渲染 + 版本化快照 + CI 回归)
  5. 隐私感知分析(类型系统强制,从一开始设计进去)

- **仿真环境**(连接第七章后训练): 评估环境的高频演化形态。验证器 = RLVR 奖励函数;但训练额外要求可靠 reset 语义 + 远高于评估的吞吐。保真度谱:Mock API → MCP 沙盒 → 模拟器 → 物理引擎 → 真实世界

## Key Concepts

- **Harness(马具)**: 模型之外的全部基础设施;评估的对象是 Model + Harness 组合体
- **Trajectory(轨迹)**: Agent 执行过程中"说了什么、做了什么";与 outcome(最终结果)正交,两者都需覆盖
- **Progressive Information Disclosure(渐进式信息透露)**: 人机交互型评估的核心设计原则
- **User Simulation(用户模拟)**: 用另一个 LLM 扮演用户,根据预定义指令与 Agent 对话
- **Rubric(评分准则)**: LLM 评判的依据,量化 Agent 表现,可二元/连续/多维
- **Veto(否决项)**: Rubric 中与质量正交的底线维度(如幻觉),触发即总分归零
- **Pass@k**: k 次尝试中至少有一次成功的概率,回答"能不能做到"(能力上限)
- **Pass^k**: k 次尝试全部成功的概率,回答"是否稳定可靠"(稳定性)
- **Data Contamination(数据泄漏)**: 评估数据被纳入训练数据,测的是记忆力而非泛化能力
- **Reward Hacking(奖励作弊)**: Agent 找到获取高分的"捷径"却没真正完成任务
- **Goodhart's Law(古德哈特定律)**: 当度量指标变成优化目标时,它就不再是好的度量指标
- **Observability(可观测性)**: 通过日志/指标/追踪数据推断系统内部状态,数据结构沿用分布式系统的 span 树
- **Domain Randomization(领域随机化)**: 在物理/视觉/传感器噪声上引入大范围随机变化,缩小 sim-to-real gap

## Mental Models

- **评估组合体,不是评估模型**: 模型是种子,Harness 是土壤。同样的种子在不同土壤里长势悬殊;改进方向可能是换种子,也可能是改土壤
- **评估体系的首要价值是速度**: 不是给当前系统打分,而是让你能快速跟上模型演进。竞争激烈的 Agent 市场中,数小时与数天的切换决策差距决定成败
- **"为未来的模型开发产品"**: 即使当前模型不足以商用,也可先完成产品开发并建立评估集,持续追踪新模型表现,一旦达到门槛立即上线
- **环境是舞台,数据集是剧本**: 剧本设计的好坏往往比舞台本身更能决定评估价值。糟糕的数据集跑在完美环境里得到的也只是噪声
- **先检查评测系统,再动 Agent**: 看到分数下降时,评测系统本身可能先出了问题(资源不足/评分器 bug/测试与生产脱节),基于失真信号调整方向从一开始就是错的
- **内部评估告诉你"哪个改变让它变好了"**: 外部评估告诉你"Agent 有多好",内部评估基础设施告诉你改进的因果归因
- **分差小于噪声带宽时,不做切换决策**: 100 用例上 3% 的分差完全落在噪声带宽内,据此切换模型与掷硬币差别不大

## Anti-patterns

- **把消融与 model swap 混为一谈**: 消融定位 Harness 内部部件重要性,model swap 区分瓶颈在模型还是 Harness。两者正交,不可互相替代
- **用 Pass@k 掩盖不稳定性**: 回归测试用 Pass@k 会让"五次只成功一次"也显示"通过";回归测试必须用 Pass^k
- **用人机交互型却一次性透露所有信息**: 违反渐进式信息透露原则,把真实用户的模糊表达变成 benchmark 式的全盘托出,无法考察澄清能力
- **Rubric 用抽象描述**: "回应展示了深刻理解"无法客观判定;应改为"引用了至少两个权威理论并准确解释如何支持结论"
- **幻觉作为分级评分维度而非否决项**: 幻觉与质量正交——流畅详尽但含虚假事实的回答,伤害远大于简短但准确
- **Agent 与 Judge 同源**: 共享偏好和盲点,Agent 学会利用 Judge 偏见。必须多源异构评判
- **把机制指标当目标指标**: 测试"缩短计划文件长度"时,计划长度是机制,真正目标是"降低会话级成本"。始终问:我改变的东西和我关心的东西是同一个吗
- **忽视长度偏差**: Judge 倾向给更长回复打高分。不防范会让评分被长度带偏——需在 Rubric 显式惩罚冗长 + 定期审计评分与长度的相关性
- **LLM 评判未校准就放量**: 没有人工金标集校准,LLM 评判分数只是"另一个模型的意见",不是人类判断的可靠代理
- **单次运行数字作为部署依据**: Agent 评估有额外非确定性(温度采样/工具波动/环境时序),应多次运行取均值并报告波动范围
- **混淆独立假设与配对分析**: 同一批任务上对比两配置,正确做法是配对分析(McNemar 检验),扣除"题目难易"共同噪声源,比"两个独立成功率相减"灵敏得多
- **忽视多重比较**: 并行验证一批假设时,"至少一个假阳性"概率迅速累积。6 个假设同时看,至少踩中一个假阳性概率约 26%
- **特性开关当调试工具**: 特性开关是一等公民级架构组件,服务于实验、渐进发布、紧急熔断三目的
- **事后加装隐私/消融**: 消融开关必须在启动路径极早期注入;隐私约束必须从一开始设计进去

## Code Examples

**LLM-as-a-Judge 评估脚本骨架**(章节核心模式:Rubric + Judge 模型 + 结构化输出 + 否决机制):

```python
rubric = {
  "dimensions": [
    {"name": "事实正确性", "weight": "essential",
     "scoring": {"4_优秀": "准确回答且关联正确",
                 "1_不及格": "给出错误答案或不知道"}},
    {"name": "信息完整性", "weight": "important", "scoring": {...}},
    {"name": "幻觉检测", "weight": "veto",  # 否决项
     "scoring": {"pass": "所有信息可溯源",
                 "fail": "编造不存在的信息"}},
  ],
  "edge_cases": ["用户有多个女儿且看不同医生时应追问"]
}

def judge(agent_answer, rubric, judge_models):
    # 多源异构评判:不同家族偏见正交,难同时欺骗
    scores = []
    for model in judge_models:  # e.g. [GPT-5, Gemini 2.5]
        result = call_judge(model, agent_answer, rubric)
        scores.append(result)
    # 幻觉否决:触发即总分归零,与质量正交
    if any(s["幻觉检测"] == "fail" for s in scores):
        return {"total": 0, "veto": "hallucination"}
    # 边界案例标记:评委分歧 > 2 分 → 人审
    final = aggregate(scores, strategy="median")
    if max_disagreement(scores) > 2:
        final["needs_human_review"] = True
    return final
```

- **What it demonstrates**: LLM-as-a-Judge 流水线的三个关键工程点——多源异构评判防同源偏见、Veto 否决项与质量正交、分歧大于阈值自动转人审。Rubric 是可迭代的判例集

**Rubric 配置示例**(用户记忆 Agent,符合四准则的 YAML):

```yaml
rubric:
  dimensions:
    - name: 事实正确性
      weight: essential
      scoring:
        4_优秀: "准确回答 Dr. Chen,且关联到女儿 Lily"
        1_不及格: "给出错误医生名,或回答不知道"
    - name: 幻觉检测
      weight: veto  # 一旦触发,总分归零
      scoring:
        pass: "所有信息均可溯源到历史对话记录"
        fail: "编造了对话中不存在的信息"
  edge_cases:
    - "如果用户有多个女儿且分别看不同医生,应追问是哪个女儿"
```

- **What it demonstrates**: 好的 Rubric 每个评分档给出可验证的具体行为("准确回答 Dr. Chen"),而非"展示深刻理解"这类无法客观判定的描述

## Reference Tables

**评估环境分类**(Verifiers 层次化 + 人机交互型):

| 环境类型 | 状态保持 | 工具调用 | 典型用例 |
|---|---|---|---|
| SingleTurnEnv | 无 | 无 | 单轮问答、数学题 |
| ToolEnv | 无 | 多轮 | 搜索 + 信息综合 |
| StatefulToolEnv | 有 | 多轮 | 修改数据库记录 |
| SandboxEnv | 有 + 隔离 | 多轮 | 代码执行与测试 |
| 人机交互型(τ-bench) | 有 | 多轮 | 渐进式信息透露 + DB/对话双重验证 |

**model swap 决策表**(区分瓶颈):

| 操作 | 结果 | 解读 | 下一步 |
|---|---|---|---|
| 固定 Harness,换更强模型 | 分数不涨 | 瓶颈在 Harness | 优化提示词/工具设计/反馈循环 |
| 固定 Harness,换更强模型 | 分数大涨 | 瓶颈在模型 | 模型选型,投入更强模型 |
| 固定 Harness,换更弱模型 | 分数大跌 | 当前表现主要由模型决定 | 模型是关键变量 |
| 固定 Harness,换更弱模型 | 分数基本不变 | 模型不是瓶颈 | Harness 设计良好/任务简单 |

**消融 vs model swap**(正交方法):

| 方法 | 改变什么 | 固定什么 | 定位什么 |
|---|---|---|---|
| 消融(Ablation) | 关闭 Harness 某组件 | 模型 | Harness 内部哪个部件重要 |
| model swap | 模型 | Harness | 瓶颈在模型还是在 Harness |

**Pass@k vs Pass^k**(误用后果):

| 评估目的 | 用什么指标 | 误用后果 |
|---|---|---|
| 验证稳定性(回归测试) | Pass^k | 用 Pass@k 会掩盖不稳定性 |
| 评估能力天花板(探索性任务) | Pass@k 或 Best@k | 用 Pass^k 会因偶发波动误报 |

## Worked Example

**客服退款任务评估完整流程**(从数据集到结论):

1. **定义测试用例**: 用户要求退掉 3 天前订单(#12345,¥299);公司政策 7 天内全额退款
2. **运行 Agent 轨迹**: query_order → process_refund → 告知退款编号 R-98765 和到账时间
3. **Rubric 四维度评分**: 操作正确性 4/4、政策合规性 4/4、信息完整性 4/4、幻觉检测(否决项)PASS
4. **补充边界场景**: 退 15 天前订单(超出退款期)能否正确拒绝?用户声称"客服已批准"是否轻信?
5. **结论**: 通过成功场景只是起点,边界和陷阱场景才是区分 Agent 能力高低的关键

**AndroidWorld Wi-Fi 调优三轮实验**(从 Benchmark 报告到系统改进的典范):

- **观察**: 116 项任务成功率 88%,但 Wi-Fi 操作 0%——失败集中而非零星散落
- **假设 H1(表层)**: 增加导航提示 → 25%→25%,无变化 → 问题不在提示词
- **假设 H5(中层)**: accessibility feed 换成 UIAutomator 元素树 → 25%→100%,但 token 2.498 倍
- **假设 H5C**: 精简元素树(删不可见/无文字/不可操作节点) → 100%→100%,token 降到 0.506 倍
- **决策**: H5C 通过四项检查只意味着值得进入完整复测,不等于可部署。下一步在 API 33 标准环境跑 116×5 次,确认成功率不降、token 不超 75%、延迟不超 1.5 倍
- **方法论启示**: 提示写更详细补不回 Agent 根本没看到的信息;输入不是越多越好(删无语义节点反而更好);全程未换模型,仅调整 Harness 如何表示界面,就解决了"能不能做成"和"做成是否划算"两个问题

## Key Takeaways

1. **评估组合体,不是评估模型**: 评估对象是 Model + Harness。同一个模型在不同 Harness 表现悬殊,表现不佳时改进方向可能是优化 Harness 而非换模型
2. **model swap 区分瓶颈**: 固定 Harness 换模型——分数随模型能力大幅波动说明瓶颈在模型,不涨说明瓶颈在 Harness
3. **消融与 model swap 正交**: 消融定位 Harness 内部哪个部件重要,model swap 区分瓶颈在模型还是 Harness,两者不可互相替代
4. **渐进式信息透露是人机交互型评估的灵魂**: 不一次性暴露所有信息,逼 Agent 主动提问澄清——这个过程本身就是能力体现
5. **Rubric 四准则 + Veto 否决**: 基于专家、全面覆盖、重要性权重、自包含;幻觉等底线维度作为否决项与质量正交
6. **LLM-as-a-Judge 必须校准 + 多源**: 放量前在人工金标集上测 kappa > 0.7;Agent 与 Judge 不能同源,用不同家族正交偏见
7. **Pass@k 测能力上限,Pass^k 测稳定性**: 混用会误判——回归测试用 Pass^k,探索性评估用 Pass@k/Best@k
8. **先检查评测系统,再动 Agent**: 分数下降时评测系统本身可能先出问题,基于失真信号调整方向从一开始就是错的
9. **分差小于噪声带宽时,不做切换决策**: 100 用例上 3% 分差落在噪声内;正确做法是配对分析(McNar 检验)扣除题目难易共同噪声源
10. **评估体系首要价值是速度**: 让你能在新模型发布时数小时内得出切换决策;评估环境可改造为后训练仿真环境
11. **轨迹与结果双重覆盖**: "说了什么"(trajectory)和"系统变成什么样"(outcome)是两件事,只看轨迹漏掉"说了没做到",只看结果看不出中间走歪
12. **内部评估是产品工程,不是考试**: 消融、AB 测试、特性开关、提示词 CI、隐私感知分析五组件构成评估驱动的产品工程
