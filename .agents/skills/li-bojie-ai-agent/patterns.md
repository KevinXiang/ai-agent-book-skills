# Patterns & Techniques — 深入理解 AI Agent

全书具体技巧、设计模式、算法的总览。格式: ## 模式名 / When / How / Trade-offs

## 上下文工程

### KV Cache 友好的上下文设计
**When to use**: 任何对延迟/成本敏感的 Agent 系统
**How**:
1. 系统提示词一旦定下来就不要改(改一个字节该位置之后全废)
2. 工具定义顺序固定、内容稳定
3. 动态信息(时间戳、状态、余额)一律追加到上下文末尾,绝不嵌入前缀
4. 子 Agent 必须与父 Agent 字节级对齐才能命中 Prompt Cache
**Trade-offs**: 前缀稳定性 vs 运行时灵活性;N 个二值条件放缓存边界前会产生 2^N 种缓存键

### Agent 状态栏注入
**When to use**: 长程任务、有明确约束、需要追踪多步骤状态
**How**: 由代码(非 LLM)维护一份聚合状态,作为 user 消息插入末尾:
- 工具调用计数("phone_call 已被调用 3/3 次")
- TODO 列表 + 当前进度
- 环境状态(系统时间、工作目录、异常提醒)
- 事件侧信道(时间间隔、地理位置)
**Trade-offs**: 弱模型补准确率(+40-54pp)、强模型省效率(思考量降一个数量级);但模型无条件信任状态栏,写错会原样传进答案

### 上下文压缩
**When to use**: 接近上下文窗口阈值,或决策质量明显下滑(上下文腐化)
**How**:
1. 上下文感知压缩(将查询意图和已有信息纳入压缩决策)最优——相比无压缩节省 76% token
2. 组合摘要优于个体摘要
3. 在两次 API 调用之间由 Agent 框架预处理,而非单次调用中修改
4. 接近阈值时批量压缩,不要每轮都压
**Trade-offs**: 频繁压缩会频繁破坏 KV Cache;压缩是有损投影,只覆盖预想维度

### Agent Skills 渐进式披露
**When to use**: 系统提示词膨胀,需要按需加载领域能力
**How**: 三层结构
1. 元数据(name + description)常驻 system prompt(~300 tokens)
2. SKILL.md 核心流程按需加载(~2K tokens)
3. 子文档选择性深入
- description 必须写成路由条件("Use when / Don't use when"),反例不是可选项
**Trade-offs**: 元数据常驻有 token 成本,但避免了启动时加载所有 Skill 正文

### 隔离优于压缩
**When to use**: 任务有独立子任务可拆分
**How**: 派生子 Agent,让它维护独立上下文,只把最终结果回传父 Agent;父 Agent 的上下文不被污染
**Trade-offs**: 子 Agent 上下文不复用父 Agent 的 KV Cache(除非字节级对齐);子 Agent 失败需要重试

## 工具设计

### 工具五分类法
**When to use**: 系统化讨论 Agent 与外界交互
**How**: 按调用方向 × 作用对象分
- 感知(Agent 主动 / 获取信息)
- 执行(Agent 主动 / 改变世界)
- 协作(Agent 主动 / 驱动其他 Agent 或人类)
- 用户沟通(Agent 主动 / 向用户传递信息)
- 事件触发(Agent 注册 / 外部触发)
**Trade-offs**: 五类各有专属设计重点(感知重粒度、执行重安全、协作重接口)

### Proposer-Reviewer 模式
**When to use**: 高风险执行工具(支付、删除、生产部署)
**How**:
1. Proposer 工具生成操作建议(如 SQL)
2. Reviewer 工具独立校验(类型检查、权限、业务规则)
3. 校验通过才执行,失败则反馈给模型重试
**Trade-offs**: 比单工具更安全,但多一次 LLM 往返

### Sidecar 旁路查询
**When to use**: 需要辅助信息但不希望污染主上下文
**How**: 派生独立的查询(子 Agent 或工具调用),只把精简结果回传
**Trade-offs**: 比 Proposer-Reviewer 轻,但不做校验;适合检索类、不适合高风险操作

### 致命三要素防护
**When to use**: 设计任何执行工具的安全机制
**How**: 同时具备
1. 非交互执行(无需用户在场)
2. 不可逆(删除、发送、支付)
3. 跨信任边界(影响外部系统)
任一要素 + 错误 = 灾难 → 必须人工确认或严格校验
**Trade-offs**: 防护过度会拖慢正常操作

### Sandbox 分级
**When to use**: 任何代码执行/文件系统访问工具
**How**: venv **不是**沙盒。真正沙盒应隔离 CPU/内存/网络/文件系统/执行时间
**Trade-offs**: 隔离越严格,Agent 能力越受限

## Coding Agent 与元能力

### Coding Agent 七工具最小集
**When to use**: 构建任何通用 Agent 的基础配置
**How**: Code Interpreter / Bash / 读文件 / 写文件 / 编辑 / Glob / Grep
**Trade-offs**: 这七工具主要覆盖感知和执行;协作、事件触发、用户沟通需另外工具

### 文件系统作为工作空间
**When to use**: 长程任务需要跨多次执行接续
**How**: 受控虚拟工作目录保存计划、中间结果、日志、最终产物
- 限定可读写路径、容量、文件类型
- 防止路径越界
**Trade-offs**: 比单一日志工具更强大,但需要管理持久化状态

### 代码即证明
**When to use**: 需要无歧义表达逻辑、需要客观对错标准
**How**: 把模糊自然语言("年龄大于 18 且已实名")转成可执行代码(`age > 18 and is_verified`),执行结果提供客观验证
**Trade-offs**: 表达严谨但牺牲灵活性

### 元能力六方向
**When to use**: 评估代码生成在编程之外的价值
**How**: 辅助思考 / 构建知识库 / 动态创造新工具 / Agent 自举 / 数据处理 / 系统集成
**Trade-offs**: 代码即元能力,但生成错误代码会放大影响

## 评估方法论

### Model Swap 决策法
**When to use**: Agent 表现不佳,需要确定改进方向
**How**:
1. 固定 Harness
2. 换更强模型 → 分数大涨 = 瓶颈在模型
3. 换更强模型 → 分数不涨 = 瓶颈在 Harness
4. 换更弱模型 → 分数大跌 = 表现主要由模型决定
**Trade-offs**: 需要评估环境支持快速模型切换;不同模型对同一 Harness 的最优配置可能不同

### LLM-as-a-Judge 实施
**When to use**: 需要自动化评判大量 Agent 输出
**How**:
1. 多源评判:用多个评委模型 + 多次采样降低偏差
2. Rubric 四准则(清晰、覆盖、可执行、有反例) + Veto 否决机制
3. 不确定时回退到人审
**Trade-offs**: 评委模型自身的偏差会被放大;高难度判断仍需人审

### 消融实验设计
**When to use**: 定位 Harness 内部哪个部件重要
**How**: 逐一关闭 Harness 组件(提示词某段、某工具、某约束),观察整体性能变化
**Trade-offs**: 与 model swap 是不同方法:消融定位 Harness 内部,model swap 区分模型 vs Harness

### 统计显著性检验
**When to use**: 评估分数差异是否真实可信
**How**: 报告标准误 / 配对分析(McNemar 检验)/ 多重比较校正
**Trade-offs**: 样本量不足时无法得出可信结论

## 后训练

### "SFT 记忆,RL 泛化"决策
**When to use**: 决定用 SFT 还是 RL
**How**:
- 任务有标准答案 + 格式稳定 → SFT 足够
- 任务需要泛化到分布外 + 有可靠奖励信号 → RL
- 两者皆可时:数据质量到位 SFT 也能泛化,奖励/环境有偏 RL 也会过拟合
**Trade-offs**: RL 工程复杂度远高于 SFT;很多场景 SFT 数据质量到位根本不需要 RL

### 奖励信号设计谱系
**When to use**: 设计 RL 训练目标
**How**: 二元奖励 → 过程奖励(PRM,对每步打分) → "奖励结果、约束过程"的验证路径惩罚
**Trade-offs**: 过程奖励更精细但 PRM 自身可能被钻空子;验证路径更可靠但需要可验证环境

### "数据和环境比算法更重要"
**When to use**: 任何后训练项目
**How**: 现成算法(PPO/GRPO)会用就行;把工程精力投入到仿真环境真实度和训练数据质量
**Trade-offs**: 算法选错会拖累项目,但通常不是决定性因素

## 持续进化

### 持续进化闭环
**When to use**: 让 Agent 从运行经验中学习
**How**: 执行任务 → 记录轨迹 → 形成信号(环境结果 + 过程规则 + LLM Rubric) → 生成候选更新 → 验证(回归/灰度/回滚) → 发布
**Trade-offs**: 所有修改必须先形成候选版本经过验证,不能直接改运行中的模型

### 四种更新载体选择
**When to use**: 决定把经验沉淀到哪里
**How**: 按成本/速度/可逆性/适用场景选
- 知识文档:便宜、慢、可逆、适合"世界是什么样的"
- Prompt/Skills:便宜、快、可逆、适合"该如何行动"
- 程序/Harness:中、中、可逆、适合"确定性的逻辑规则"
- 模型参数:贵、慢、不可逆、适合"无法用上面三种表达的直觉能力"
**Trade-offs**: 优先用前三种;模型参数更新作为最后手段

### LLM Rubric 七维评估
**When to use**: 缺乏客观指标时从轨迹提取学习信号
**How**: 用 LLM 按 Rubric(如任务完成度、合规性、效率等维度)打分
- uncertain 时必须有证据支持
- 与承诺—行动一致性交叉验证
**Trade-offs**: Rubric 主观,需要校准;比客观指标噪声大

## 多模态与实时

### 语音架构三范式选择
**When to use**: 设计语音 Agent
**How**:
- 级联(VAD-ASR-LLM-TTS):成熟可控、延迟高(0.95-2.3s + 排队放大)
- Omni 端到端:单模型但仍轮流说话、延迟低
- 全双工(Moshi/GPT-Live):边听边说、可打断、资源消耗大
**Trade-offs**: 三范式非新旧替代而是并存取舍

### 快慢解耦架构
**When to use**: 实时响应与深度思考矛盾
**How**: 快模型负责实时对话,慢推理模型当"军师"在后台思考,通过文字或 Latent Bridge 传递结果
**Trade-offs**: 文字是高损耗通道;Latent Bridge 理论更优但工程复杂

### Computer Use 感知-思考-行动循环
**When to use**: 让 Agent 操作 GUI
**How**: 截图 → 视觉定位(SoM/DOM/坐标预测)→ 决定动作(点击/输入/滚动)→ 执行 → 重新截图验证
**Trade-offs**: 逐帧截图有延迟;坐标缩放需要双向映射

## 多 Agent 协作

### 上下文共享决策
**When to use**: 设计多 Agent 系统的第一步
**How**:
- 共享上下文:信息不丢失,可回顾任意阶段细节;但上下文快速膨胀(类似线程)
- 不共享上下文:模块化、隔离性好、易扩展;需显式通信机制(类似进程)
**Trade-offs**: 共享有信息完整性优势,不共享有工程整洁性优势

### 三种通信机制选择
**When to use**: Agent 间(不共享上下文时)如何传递信息
**How**:
- 工具调用参数:同步、类型确定、结构清晰(消息传递)
- 共享文件系统:产物大或需持久化(共享内存)
- 消息总线:异步、解耦、支持一对多(消息传递)
**Trade-offs**: Go 名言——共享内存快但并发冲突留给使用者;消息传递需多写编排代码但数据归属清晰

### 新信息判据
**When to use**: 多 Agent 何时真正优于单 Agent
**How**: 只有当多 Agent 能带来新信息(不同视角/不同工具/不同模型)时才优于单 Agent;否则只是增加协调开销
**Trade-offs**: 多 Agent 不是万能药;简单任务单 Agent 更高效
