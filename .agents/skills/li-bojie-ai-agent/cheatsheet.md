# Cheatsheet — 深入理解 AI Agent

> 一页纸决策指南。每一行都帮你**做一个决定**,而不是查一个词(查词看 glossary,看流程看 patterns)。

## 顶层公式(刻在脑子里)

| 场景 | 公式 |
|---|---|
| Demo / 概念讨论 | `Agent = LLM + 上下文 + 工具` |
| 生产系统 / 可靠性讨论 | `Agent = Model + [上下文 + 工具 + 约束 + 验证 + 纠正]` |

## 一、Agent 表现不佳时,先问这三个问题

```
1. 模型能看到所需信息吗?(观察空间)
   → 不能:扩上下文,不要换模型
2. 模型能采取所需行动吗?(动作空间)
   → 不能:加工具,不要换模型
3. 信息和行动都到位了仍出错?
   → 缺约束/验证/纠正 → 优化 Harness,不要换模型
```

**核心判据**: 大多数"需要更聪明模型"的问题,其实是接口/Harness 问题。

## 二、上下文设计决策表

| 我要做… | 决策 | 原因 |
|---|---|---|
| 在系统提示词嵌入时间戳 | ❌ 不要 | 改一个字节该位置后全废 KV Cache;改成 user 消息追加末尾 |
| 工具按使用频率动态排序 | ❌ 不要 | 破坏缓存;固定顺序对模型选择几乎无影响 |
| 用滑动窗口控制长度 | ❌ 不要 | 破坏前缀一致性 + 丢失关键工具结果 → 死循环 |
| 把消息转成"USER: ⋯ ASSISTANT: ⋯"文本 | ❌ 不要 | 偏离训练格式,模型需额外消耗注意力推断边界 |
| 让 LLM 维护状态栏 | ❌ 不要 | 把"扫描长上下文"难题搬家;用 20 行正则代码维护 |
| 删原始上下文只留状态栏 | ⚠️ 谨慎 | 状态栏是有损投影,问题落到没算过的维度准确率断崖式崩塌 |
| 动态状态(余额/计数/时间) | ✅ 作为 user 消息追加末尾 | 不破坏前缀缓存 + 紧邻生成位置获最高注意力 |
| 系统提示词 / 工具定义 | ✅ 前缀稳定不动 | 持续复用 Prompt Cache |
| 长程任务的状态追踪 | ✅ 注入 Agent 状态栏 | 弱模型补准确率,强模型省效率 |

## 三、上下文压缩——选哪种?

| 策略 | Token 节省 | 决策 |
|---|---|---|
| 无压缩 | 0% | ❌ 上下文腐化会导致失败 |
| 个体摘要 | 89% | ⚠️ 反而膨胀(token 多) |
| 组合摘要 | 96% | ✓ 可用 |
| **上下文感知** | **97%** | **✓ 最优**(将查询意图纳入压缩决策) |

**核心原则**: 压缩不只是省长度,**更重要的是提升思考质量**——总结后的知识比原始形式更利于模型使用。

## 四、工具设计决策树

```
这次工具调用是 Agent 主动 还是 外部触发?
├─ Agent 主动
│   ├─ 目的是获取信息 → 感知工具(粒度权衡、输出量控制)
│   ├─ 目的是改变世界 → 执行工具
│   │   └─ 同时满足"致命三要素"?(非交互 + 不可逆 + 跨信任边界)
│   │       ├─ 是 → 必须人工确认 / Proposer-Reviewer / Sidecar
│   │       └─ 否 → 普通执行 + 沙盒
│   ├─ 目的是驱动其他 Agent/人 → 协作工具(spawn_subagent / send_message)
│   └─ 目的是向用户传递信息 → 用户沟通工具
└─ Agent 注册、外部触发 → 事件触发工具(邮件/定时/Webhook)
```

## 五、工具该通用还是专用?

| 维度 | 通用工具 | 专用工具 |
|---|---|---|
| 适合 | 组合、探索、低风险任务 | 高风险、强业务约束(支付/删除/部署) |
| 设计 | 参数清晰 + 沙盒隔离 + 资源上限 | 参数明确 + 权限受限 + 全程可审计 + 人工确认 |

**核心原则**: 通用基础能力用于组合与探索;专用工具用于约束高风险和强业务规则操作。

## 六、评估:瓶颈在模型还是 Harness?

```
固定 Harness,换更强模型:
├─ 分数大涨 → 瓶颈在模型 → 换模型
├─ 分数不涨 → 瓶颈在 Harness → 优化提示词/工具/反馈循环
└─ 换更弱模型分数大跌 → 表现主要由模型决定 → 任务难度本身高

固定模型,关掉 Harness 某组件(消融):
└─ 看分数掉多少 → 该组件的真实贡献
```

## 七、后训练:SFT 还是 RL?

| 任务特征 | 推荐 | 原因 |
|---|---|---|
| 有标准答案 + 格式稳定 | SFT | 便宜、快、稳 |
| 需要泛化到分布外 | RL | "SFT 记忆,RL 泛化"(实验结果,非普遍属性) |
| 有可验证奖励(代码/数学) | RLVP | 客观奖励,不需人类标注 |
| 需要人类偏好对齐 | RLHF | 训练奖励模型再 RL |
| 不确定 | 先 SFT | 数据质量到位时 SFT 也能泛化;很多场景根本不需要 RL |

**两条铁律**:
1. **"SFT 记忆,RL 泛化"** 是实验结果,不是普遍属性
2. **"数据和环境比算法更重要"** ——现成算法会用就行,把精力投到仿真环境真实度和训练数据质量

## 八、奖励信号——选哪种?

| 类型 | 何时用 | 风险 |
|---|---|---|
| 二元奖励(对/错) | 简单任务、有明确答案 | 信号稀疏,样本效率低 |
| 过程奖励(PRM,每步打分) | 多步推理 | PRM 自身可能被钻空子(reward hacking) |
| 验证路径("奖励结果、约束过程") | 可验证环境(代码/数学) | 最可靠,但需要可验证 |
| 人类偏好 | 主观任务、对齐 | RLHF 成本高、奖励模型有偏 |

## 九、经验沉淀到哪里?(四种更新载体)

按"**优先用前三种,模型参数作为最后手段**"排序:

| 载体 | 成本 | 速度 | 可逆性 | 适合 |
|---|---|---|---|---|
| 知识文档 | 便宜 | 慢 | 可逆 | "世界是什么样的" |
| Prompt / Skills | 便宜 | 快 | 可逆 | "该如何行动" |
| 程序 / Harness | 中 | 中 | 可逆 | "确定性的逻辑规则" |
| 模型参数 | 贵 | 慢 | **不可逆** | "无法用上面三种表达的直觉能力" |

**核心判据**: 保存经历 ≠ 从经历中学习。把轨迹塞进向量库不会自动完成跨案例比较;学习发生在"评价、对照、归纳、验证"之后。

## 十、多 Agent 真的需要吗?

```
任务能否由单个 Agent 在合理上下文窗口内完成?
├─ 能 → 单 Agent(简单透明,优先)
└─ 不能或需要不同模型/工具 → 多 Agent
    └─ 多 Agent 能带来新信息吗?(不同视角/工具/模型)
        ├─ 能 → 设计协作架构
        └─ 不能 → ❌ 多 Agent 只增加协调开销,不如单 Agent
```

## 十一、关键阈值与默认值

| 场景 | 阈值 / 默认 | 出处 |
|---|---|---|
| Agent 死循环防护 | 必须设 `max_iterations` 上限 | Ch 2 |
| 缓存命中率参考 | Prompt Cache 命中率约 98.5% | Ch 2 |
| 缓存读取成本 | 约首次计算的 1/10 | Ch 2 |
| 状态栏让弱模型准确率提升 | +40 至 54 个百分点 | Ch 2 |
| 状态栏让强模型思考量降低 | 一个数量级(八九成) | Ch 2 |
| 上下文感知压缩节省 | 比无压缩节省 76% token | Ch 2 |
| 端侧小模型可用性 | 0.6B 模型在 M2 上 >100 token/s | Ch 2 |
| Coding Agent 最小工具集 | 7 个(Code Interpreter/Bash/读/写/编辑/Glob/Grep) | Ch 5 |
| 语音交互延迟红线 | 停顿 >2 秒用户焦躁 | Ch 9 |

## 十二、Smells(闻到这些味道就要警惕)

| 闻到… | 大概率问题 |
|---|---|
| "我们需要一个更聪明的模型" | 没诊断就跳到换模型;先查观察空间/动作空间/Harness |
| 系统提示词里有 `{current_time}` | 动态前缀,每次破坏整个 KV Cache |
| Agent 反复调用同一工具 | 缺工具结果(Verify 缺失)或滑动窗口丢历史 |
| "把所有规则塞进系统提示词" | 上下文腐化 + 注意力稀释 → 用 Skills 按需加载 |
| 让 Agent 直接训练自己 | 错误经验和提示注入被固化 → 必须候选版本 + 验证 |
| 多 Agent 但共享同一模型同一工具 | 没有新信息 → 只增加协调开销 |
| "RL 比 SFT 好" | 无条件判断;很多场景 SFT 数据到位就够 |
| 用 LLM 维护状态栏 | 把扫描长上下文难题搬家 → 用代码 |
| 子 Agent 与父 Agent 提示词不一致 | 无法命中 Prompt Cache,费用/延迟翻倍 |
| venv 当沙盒用 | venv 不是沙盒;真沙盒需隔离 CPU/内存/网络/FS |
